## Bug fix: JPEG thumbnails stayed blank forever after import (2026-07-27)

User report, tested and root-caused rather than assumed. Symptom: after importing a JPEG, its Library grid cell stayed a blank placeholder indefinitely, even well after import finished.

- **Metadata was not actually broken** — checked first since the user's report bundled it with the thumbnail symptom. Ran the real extraction path against a real Sony NEX-6 JPEG (copied from a real photo on this machine, not synthetic) both directly (`extract_from_jpeg`) and through the full `import_files` → catalog round trip: camera/lens/exposure/captured-at all landed correctly and immediately. Cell selection wiring (`GridCell` → `LibraryGrid` → `selectedId` → `MetadataPanel`) was also confirmed correct by inspection. Most likely explanation for "no metadata" in the original report: the same blank-looking cell probably discouraged clicking into it, or the user's own test JPEG genuinely had no EXIF (common for downloaded/screenshotted images) — not a code bug.
- **The thumbnail symptom was real, and root-caused, not just patched around.** JPEG thumbnail generation is a fire-and-forget background pass (`import::generate_missing_thumbnails`, M2 Slice 1) that runs *after* the import command already returned its response — by design, so a JPEG-heavy import doesn't block on it. But `+page.svelte` only ever calls `refresh()` (→ `listImages()`) once, right after import (and once more at startup) — nothing ever told it to look again once the background pass actually finished. So the frontend's one-shot snapshot permanently showed `thumbnail_path: null` for the rest of the session, regardless of how long the background pass took or whether it succeeded.
- **Confirmed via a real reproduction, not just code reading**: imported a real 8MB/4000×2658 JPEG through the actual `import_files` command inside the running app, captured the frontend's `images` state immediately after import (thumbnail_path: null, as expected) and again via a direct backend query 4s later (still null) — proving the staleness wasn't just theoretical. A follow-up direct-Rust timing test found the actual cause of *that specific* run's failure: in this project's unoptimized dev build, decoding+resizing a real photo this size took **4.83s**, longer than the 4s window before the app closed — the background `spawn_blocking` task gets abandoned along with the process on quit, so a thumbnail generation that hasn't finished by the time the app closes is lost until the next startup catch-up pass. (Release builds should be dramatically faster since JPEG decode is CPU-bound and debug/dev builds are unoptimized — but the underlying staleness bug would still show up as a delay-then-never-updates symptom in *any* build, just a shorter delay.)
- **Fix**: `+page.svelte` gained `pollUntilThumbnailsReady()` — after any `refresh()` that could have left `thumbnail_path: null` rows (post-import, and the initial startup refresh, which races the app's own startup catch-up pass the same way), it polls `listImages()` every 1.5s (capped at 10 attempts, ~15s total) until no currently-tracked image has a null thumbnail. Bounded deliberately — a genuinely-failed decode (a real, permanent error) shouldn't poll forever; it just stops and leaves the placeholder, which is the correct outcome in that case.
- **Verified the fix actually works, not just that it compiles**: re-ran the same real-photo import through the running app, this time letting `runImport`'s own new polling logic run for real (not artificially closing early) — the frontend's own `images` state went from `thumbnail_path: null` immediately after import to the real generated thumbnail path ~4–8s later, entirely on its own, no manual refresh or restart needed.
- `cargo test --lib`: 42/42 passing (no test changes needed — this was a frontend-only fix, the backend's background-generation behavior was already correct and already covered).

## M2 Slice 2 — Full metadata (EXIF + IPTC): DONE (2026-07-27)

Planned via a reviewed design doc — the review corrected a real premise error (JPEG metadata extraction and `jpeg_decode.rs`'s existing EXIF-orientation read are NOT the same parse and don't share one `exif::Reader` call — they run at different times, at import vs. in the background thumbnail pass) and flagged a real regression risk (IPTC's save-on-blur pattern reintroducing the exact "lose an edit on window close" bug class M1 Slice 6 fixed for the Develop edit stack), both incorporated below. **Scope cut, named explicitly**: EXIF + IPTC only. Embedded color-profile reading/application is ADR-0004's own already-flagged, still-unwired, highest-risk item — genuinely separate scope, deferred to its own future slice rather than bundled in here.

- **New module `metadata.rs`**: `extract_from_raw` uses `rsraw`'s own metadata getters (`normalized_make`/`normalized_model`/`iso_speed`/`aperture`/`shutter`/`focal_len`/`datetime`/`lens_info`) — confirmed via the vendored crate's source that these read header fields `RawImage::open` already populates, no `unpack()`/`process()` needed, so calling this at the exact point `import_paths` already has a live `RawImage` is free, no new parse. `extract_from_jpeg` is a genuinely new `exif::Reader` read at import time (the premise correction above) pulling Make/Model/LensModel/PhotographicSensitivity (not `ISOSpeedRatings` — that tag name doesn't exist in this crate; the modern EXIF 2.3+ name is `PhotographicSensitivity`)/FNumber/ExposureTime/FocalLength/DateTimeOriginal.
- **IPTC's three fields split across two tables, not all on one — a deliberate asymmetry, documented on `ImageSummary` so it doesn't read as an oversight**: `caption` lives on `image_versions` (plausibly diverges per virtual copy, matching the character of the already-per-version `rating`/`flag`/`color_label`); `copyright`/`contact` live on `images` (identify the photographer/owner, invariant across every copy of a given original — closer in spirit to EXIF than to culling state).
- **`add_image_with_edit_stack` (the M1 Slice 6 atomic-insert method) gains a `&ImageMetadata` parameter**, inserted as part of the same transaction as the image + edit-stack rows — same reasoning as that slice's own fix: metadata insertion failing partway through import shouldn't be a new way to produce an inconsistent row. Three new setters (`set_caption`/`set_copyright`/`set_contact`), matching the existing granularity of `set_rating`/`set_flag`/`set_color_label`. IPTC writes go straight to the catalog, never touch the source file — satisfies the hard "never modify originals" constraint with no IPTC-*writing* library needed at all.
- **New frontend: `MetadataPanel.svelte`**, a third Library column (`flex: none; width: 240px`, matching `.rail`'s existing pattern — `LibraryGrid`'s own column-count math is purely `$derived` off `bind:clientWidth`, so this didn't break anything). Shows the selected image's EXIF as static rows (Camera, Lens, a combined "1/125 · f/8 · ISO 100"-style Exposure line, Captured) plus three editable IPTC fields (caption, copyright, contact) that save on blur.
- **Real regression, fixed here per the design review, not left implicit**: `+page.svelte`'s `onCloseRequested` handler (from M1 Slice 6) used to only flush the Develop edit-stack's pending write — a caption typed but not yet blurred when the user clicks the window's close button would have been silently lost, the exact bug class that slice fixed for sliders. Fixed by tracking a `pendingIptcSave` promise (same shape as `pendingSave`) and, in the close handler, calling `document.activeElement?.blur()` before the pending-work check (forces any in-progress edit's blur-save to fire) then `await Promise.all([flushEditStack(), pendingIptcSave ?? Promise.resolve()])` before `destroy()`.
- **Real bug found empirically, not by review — a genuine migration gap**: `catalog.rs`'s `migrate()` was `CREATE TABLE IF NOT EXISTS` only, which is a no-op against a table that already exists. This project's own dev catalog (in continuous use since M1) still had the pre-Slice-2 schema, so the first real run against it failed every metadata-bearing import with a raw SQL error ("no such column: camera_make") and the app hung (an unhandled promise rejection from `invoke()` meant the smoke-test script's `getCurrentWindow().close()` call was never reached). This is the project's first schema change since `content_hash`/`file_size`, which happened to land before any real catalog existed to migrate — so the gap was latent, not previously hit. Fixed with a real (if minimal) migration step: a set of `ALTER TABLE ... ADD COLUMN` statements run after the `CREATE TABLE IF NOT EXISTS` text, each tolerating a "duplicate column name" error (already-applied) while still propagating any other error. New regression test (`migrate_adds_new_columns_to_a_pre_existing_catalog_without_losing_data`) builds the exact pre-Slice-2 schema by hand with one pre-existing row, runs `migrate()`, and confirms the row survives and a metadata-bearing insert succeeds afterward. **This is worth remembering going forward**: every future column addition needs its own `ALTER TABLE` line here, not just an edit to the `CREATE TABLE` text — the module doc comment was updated to say so explicitly.
- **Real, if minor, finding along the way**: ImageMagick's `convert -set exif:Tag value` does **not** actually write an EXIF segment on this machine (ImageMagick 7.1.2) — confirmed via `identify -verbose` showing zero `exif:*` properties on the output despite `convert` reporting success. Switched to `little_exif` (a real, independently-published Rust EXIF-writing crate, added as a `--dev` dependency) to build genuinely EXIF-bearing test JPEGs instead.
- **Timezone-fragile test caught before it could flake in CI**: `rsraw::datetime()` converts to the *local* system timezone (confirmed CST/+08:00 in this dev sandbox), so a test asserting a full RFC3339 string with a hardcoded offset would pass here and fail on a UTC CI runner (or vice versa). Fixed to assert only the date prefix.
- **Verified empirically through the real app, twice**: cleared/reused the real catalog, imported a real RAW sample and a real `little_exif`-generated EXIF-bearing JPEG via a temporary self-driving diagnostic route (same pattern used for M1 Slice 6's own close-handler verification) — confirmed via `sqlite3` against the actual catalog file that the JPEG's Camera/Lens/Exposure/Captured fields landed exactly as written (Fujifilm X-T5, ISO 800, f/2.8, 1/500s, 35mm, XF35mmF1.4 R, 2025-11-02T14:22:10). Then re-ran the close-handler race specifically: called the real `handleCaptionChange`/`handleCopyrightChange`/`handleContactChange` handlers and immediately requested `getCurrentWindow().close()` with **no artificial delay** (an earlier pass of this same test used a 200ms delay before closing, which would have passed even with a broken fix, since the writes would very likely have already landed on their own by then — corrected once noticed, not left as a false-confidence pass) — the app still exited cleanly and the values were confirmed on disk via `sqlite3` afterward, a real confirmation the `Promise.all` wait actually holds the close.
- `cargo test --lib`: 42/42 passing (metadata extraction for both RAW and JPEG, atomic-insert-with-metadata, the three IPTC setters' round-trip, and the migration regression test). `npm run check`: 0 errors, 0 warnings.

## M2 Slice 1 — Multi-file import dialog + JPEG format support: DONE (2026-07-27)

Planned via a reviewed design doc — the review caught a real validation-order bug (a naive JPEG implementation would have given corrupt JPEGs *weaker* crash-safety than corrupt RAW files) and a missing EXIF-orientation fix (portrait JPEGs would otherwise render sideways) before either was written, both incorporated below. A real bug was also found empirically during testing, not by review: extending JPEG recognition broke two existing tests because their fixtures nested the thumbnail output directory *inside* the scanned directory — once `.jpg` became a recognized source extension, `collect_candidate_files` started picking up the previous run's own generated thumbnails as new "source images" on a second scan. Fixed by making every test's thumbnail dir a sibling of its scan dir, matching how the real app already keeps `<app data dir>/thumbnails` separate from any real photo folder.

- **New module `source_decode.rs`**: format dispatch (`ImageFormat::from_path`, replacing `import.rs`'s old standalone `RAW_EXTENSIONS`/`has_raw_extension` with one shared source of truth for both import-time filtering and decode-time dispatch), a unified `DecodeError`, and `decode_preview`/`decode_develop_preview` facades that route to `raw_decode.rs` (unchanged, RAW-only) or the new `jpeg_decode.rs`. `DecodedPreview` moved here from `raw_decode.rs` to avoid a module cycle (`source_decode` needs `raw_decode` for dispatch, so `raw_decode` can't also need `source_decode` just to name its return type). `preview_cache.rs` and `export.rs` switched their imports to the new dispatch module — call-site swap only, no logic changes to either.
- **New module `jpeg_decode.rs`**: one decode function (unlike RAW, JPEG has no demosaic step to skip, so there's no meaningful draft-vs-full distinction), via the `image` crate. **Applies EXIF orientation correction** (new `kamadak-exif` dependency, reads just the Orientation tag) before returning — the `image` crate's own decode doesn't auto-apply this, and unlike RAW (where LibRaw already handles camera rotation internally), an untouched JPEG would render sideways for any portrait/rotated shot. In scope for this slice specifically because it's a visible-correctness bug, not a missing-metadata gap (full EXIF display is a later slice).
- **`import.rs`'s per-file loop now branches by format, with the validity-gate ordering the review flagged as the real substance of this change**: RAW keeps its existing pre-insert gate (`RawImage::open`) — a corrupt file is never cataloged. JPEG's pre-insert gate is a **cheap header-only read** (`image::ImageReader::with_guessed_format().into_dimensions()`, no full IDCT decode), mirroring RAW's gate cost, not a full `jpeg_decode::decode()` call — a corrupt JPEG is likewise never cataloged, not cataloged-with-just-no-thumbnail (the weaker semantics a naive "decode as the thumbnail step" implementation would have produced). JPEG's actual thumbnail generation is **deferred to a new background pass** (`generate_missing_thumbnails`, same shape as `preview_cache::pregenerate_missing`, triggered the same two ways: after every import, and once at startup) rather than synchronous — a full JPEG decode is categorically heavier than RAW's cheap embedded-thumbnail extraction, and running it inside the import loop would have visibly slowed a JPEG-heavy import with zero progress feedback. `GridCell.svelte` already renders a placeholder for a null `thumbnail_path`, so no frontend change was needed for the gap between import and the background pass completing. As a free side effect of being format-generic, this background pass also backstops RAW images whose embedded thumbnail wasn't JPEG-format (previously permanently thumbnail-less, now recoverable).
- **Shared per-file core**: `scan_and_import` (directory walk) and the new `import_files` (explicit path list) both call one `import_paths` function — extracted this slice specifically so multi-file import doesn't duplicate the RAW/JPEG branching logic.
- **New `import_files`/`get_supported_extensions` Tauri commands**, and a new "Import Files…" button in `+page.svelte` (titlebar and empty-state) alongside the existing "Import Folder…" — confirmed via the dialog plugin's own type defs that `directory`/`multiple` are independent booleans with no combined "pick files or a folder" mode, so these are genuinely two separate entry points, not a config tweak to one dialog. The file-picker's extension filter is populated from `get_supported_extensions` at runtime rather than a hand-duplicated JS list, avoiding future drift as more formats are added.
- **Verified empirically, not just via tests**: cleared the real catalog, imported a real RAW file and a real JPEG together via the actual `import_files` command (bypassing the native OS dialog, which can't be scripted, the same substitution used throughout this project) — both cataloged correctly, the JPEG's `thumbnail_path` was null immediately after import and became a real, valid 300×200 JPEG on disk ~1.5s later once the background pass ran, `get_develop_preview` for the JPEG produced a real, valid 300×200 PNG through the new dispatch path, and the RAW file's synchronous embedded-thumbnail extraction still worked correctly (regression check on the refactored per-file loop).
- `cargo test --lib`: 34/34 passing (10 new: format-dispatch tests, EXIF-orientation-transform tests against real generated JPEGs, the validity-gate-ordering test for corrupt JPEGs, the background-thumbnail-backfill test). `npm run check`: 0 errors, 0 warnings.
- **Named, not fully tested**: no real photo with actual EXIF rotation metadata was available in this environment to test end-to-end — the orientation *transform math* is tested directly and deterministically (real assertions against known pixel-dimension outcomes for each of the 8 EXIF orientation values), and the *fallback-to-no-op* path is tested against a real (synthetic, no-EXIF) JPEG, but a full "real rotated photo decodes right-side-up" integration test wasn't possible here.

## M1 Slice 6 — Crash-safety hardening + dogfood pass (final M1 slice): DONE (2026-07-26)

Exists to satisfy M1's own exit criteria: "No data loss across app restarts or crashes mid-edit," and "this is the first installable, dogfoodable build." Planned via a reviewed design doc — the review caught a bug that would have silently defeated the flagship fix before any code was written, and one real gap not in the original scope.

- **`flushEditStack()` in `+page.svelte` didn't return its write promise** — every `await flushEditStack()` call site (three existed already: `switchModule`, `openDevelop`, Slice 5's `handleExportClick`) resolved on the next microtask regardless of whether the actual `set_edit_stack` IPC call had landed. Fixed to return the real promise, and to track an in-flight `pendingSave` separately from the debounce timer (a second flush/close can happen while a previous flush's write is still resolving). This was the load-bearing fix everything else in this slice depended on.
- **New: flush the pending edit before the window actually closes.** `getCurrentWindow().onCloseRequested` intercepts a graceful quit, flushes (now correctly awaited), then `destroy()`s. **Named limitation, not hidden**: this protects a graceful quit only (close-button click, or another OS "please close" request routed through the same pipeline `.close()` itself uses per Tauri's own docs) — it cannot help against SIGKILL/a hard crash, which bypasses every in-process handler. Whether macOS Cmd+Q routes through this same path is unverified in this environment.
- **Real capability gap found and fixed along the way**: the app's `capabilities/default.json` only granted `core:default`, which does **not** include `core:window:allow-close`/`allow-destroy`. Without these, the new close-flush handler would have called `event.preventDefault()` and then failed to actually close the window — a user could have gotten **stuck unable to quit the app at all** after dragging a slider, which is arguably worse than the original data-loss bug. Found empirically (the first close-flush smoke-test run failed with `"window.close not allowed"`), not by code review — confirms the value of actually running this rather than assuming Tauri's default permissions were sufficient.
- **Import's two-row insert made atomic**: `import.rs` used to call `add_image_with_metadata` then a separate `add_edit_stack` — two independent auto-commit statements. New `Catalog::add_image_with_edit_stack` (`catalog.rs`) wraps both in one `unchecked_transaction`. Per the design review: a crash between the two old statements left an `images` row `list_images()` silently excluded (no matching `image_versions` row) but that `find_by_hash` still matched on every future import scan — the file became **permanently unimportable** through the normal UI, a disproportionately bad failure mode for how narrow the window was. Fixed by inspection (transactions are correct-by-construction), not by empirically reproducing the microsecond-scale race — padding an import with duplicate-content files to "widen" the window was considered and correctly rejected by the review as not actually testing what it would claim to.
- **SQLite hardened**: WAL mode + `synchronous=NORMAL` on `Catalog::open` (not `open_in_memory`). **Honest framing, not oversold**: the prior default (rollback journal + SQLite's own implicit `synchronous=FULL`) was already durable against process crashes — this doesn't close an existing hole in the "no data loss" criterion (the two fixes above do that). What it actually buys today is more forward-looking hygiene than a realized fix, since `AppState.catalog` is a single `Arc<Mutex<Catalog>>` around one connection — everything already serializes through Rust's own Mutex regardless of journal mode. Cheap and standard to add regardless. Used `pragma_update_and_check` (not `pragma_update`) specifically for `journal_mode`, since `pragma_update` silently swallows the row SQLite returns for that particular pragma and would "succeed" even if WAL failed to engage.
- **Verified empirically, not just by code review** (three real tests through the actual app, no tool to click/screenshot the native window so script-driven triggers substitute for physical interaction, same pattern used throughout this project):
  1. A throwaway `/m1-slice6-smoke` route scheduled a real debounced edit-stack write, then called the real `getCurrentWindow().close()` ~10ms later (well inside the 250ms debounce window) — the close-flush handler intercepted it, and after the process fully exited, `sqlite3` confirmed the edit landed (`exposure: 0.42`, the scheduled value) and WAL mode was active (`-wal`/`-shm` files present, `PRAGMA journal_mode` reports `wal`).
  2. `kill -9` against a running instance with only already-persisted state: `PRAGMA integrity_check` returned `ok` afterward, row counts and edit-stack content were unchanged — confirms the baseline persisted-write path was never the risky part.
  3. `kill -9` timed against a real `import_folder` call (via a throwaway `/m1-slice6-import-kill-smoke` route): the import (only 1-2 real files available in this environment, see below) completed before the kill landed in both attempts — this environment's real files process too fast to reliably land a kill inside the transaction window via external shell-script timing, which is itself consistent with the atomic fix making that window very small. `PRAGMA integrity_check` was `ok` afterward regardless.
- **Real dogfood pass, honestly scaled**: the actual M1 workflow (import → cull → develop → export) was exercised end-to-end across every slice's own verification this session, using this environment's 2 real CC0 sample RAW files — not PRD's literal "hundreds of RAW files" scale, which no larger real RAW set is available here to test. Named plainly rather than implied as tested at scale.
- `cargo test --lib`: 25/25 passing (new `add_image_with_edit_stack_inserts_both_rows_atomically` test). `npm run check`: 0 errors, 0 warnings.

**New named, deferred risks** (this slice's job is naming crash-safety gaps honestly, not fixing every one immediately):
- **`std::sync::Mutex` poisoning**: every catalog command does `state.catalog.lock().map_err(...)?`, and `catalog.rs` uses `.expect(...)` on EditStack JSON (de)serialization. A panic while the lock is held would poison it permanently for the process's lifetime — every later catalog call fails until the user force-quits and restarts. Low-probability today (nothing currently writes invalid JSON), not fixed this slice.
- **A truncated preview PNG from a crash mid-write during background pregeneration would be cached as permanently broken**: `ensure_develop_preview_for_hash`'s cache-hit check (`preview_cache.rs`) is just `out_path.exists()` — a partial file from an interrupted write would pass that check forever, then fail `image::image_dimensions` on every subsequent attempt, with no automatic retry/regeneration. Found while designing (not empirically reproducing) the pregeneration-kill test above. Lower severity than the catalog-side fixes in this slice (affects one cached preview file, not the catalog or the original RAW file — recoverable by deleting the one bad cache file), not fixed this slice.

## M1 Slice 5 — Export pipeline (single-image, JPEG, CPU render): DONE (2026-07-26)

Scope cut per the plan, following the same pattern Slice 3 used for Develop: JPEG only, single image only (Library has no multi-select UI yet — batch is a named follow-up, not silently dropped), long-edge-or-original resize, one quality setting, no color management (none exists anywhere in the pipeline yet), no live progress stream (a single request-response, same "no visible progress UI" call already made for Slice 4's background job).

- **New module `app/src-tauri/src/export.rs`**: `export_one`/`export_batch` decode the source RAW at **full native resolution** via `raw_decode::decode_preview` (previously dead code, now a real caller — deliberately *not* Slice 4's 2048px-capped Develop preview cache, a different buffer for a different purpose), apply the current edit stack, optionally resize to a long-edge cap (Lanczos3), and JPEG-encode to a collision-safe filename (`stem.jpg`, `stem-1.jpg`, ...) in the user's chosen destination folder.
- **`apply_edit_stack` mirrors `DevelopCanvas.svelte`'s WGSL shader formula exactly** (same order: exposure → contrast → saturation, same math, kept in `f32`) so an export matches what Develop shows — CPU-side per ADR-0004's explicit assignment of the export path to native Rust (no `<100ms` latency requirement there, unlike the interactive canvas). Tested against the same hand-derived expected value the shader's own numeric test already used (`(153,51,51)` + exposure `+0.5`/contrast `+10`/saturation `+30` → `(255,56,56)`, `±2` tolerance) — not required to be byte-identical to the GPU's actual output, which the project's own existing shader test doesn't require either.
- **New `export_images` Tauri command** resolves each item's `EditStack` under a brief catalog lock, then releases it before the slow decode+resize+encode work — matters more here than Slice 4's background job, since `AppState.catalog` is one `Mutex` shared by every command and this is a request-response call the user is actively waiting on; holding the lock across a multi-second full-res export would have visibly stalled unrelated UI actions (rating a photo, switching Library selection) elsewhere in the app.
- **Real correctness fix caught during planning, not left implicit**: Develop's edit-stack autosave is debounced 250ms. Triggering Export right after a slider drag could otherwise export the *previous* persisted stack, not what's on screen — fixed by flushing the pending save before opening the export dialog (`+page.svelte`'s `handleExportClick`), same discipline as the two existing flush call-sites.
- **Frontend**: `app/src/lib/api/export.js` (thin command wrapper), new `ExportDialog.svelte` (destination-folder picker reusing the existing dialog-plugin pattern, long-edge input, quality input, Export button disabled while in flight — same `disabled={importing}` discipline `handleImport` already uses, which is also what keeps the inherently-check-then-write collision-avoidance logic a non-issue in practice), a new "Export…" button in the titlebar next to Import, enabled whenever there's a "current image" (the open Develop image, or the selected Library image).

## M1 Slice 4 — Develop preview cache: DONE (2026-07-26)

Slice 3 shipped Develop decoding the source RAW fresh on every open (explicitly deferred as "correct, simple; caching is a later optimization not a correctness requirement"). In practice this was slow enough that the user asked for a Lightroom-style pre-generated preview mechanism, which was first folded into the roadmap ([PRD §7.2](PRD/PRD.md#72-import)/[§7.6](PRD/PRD.md#76-performance--data-integrity-cross-cutting-not-a-feature-but-a-requirement), [MILESTONES.md's M1 section](PRD/MILESTONES.md#m1--mvp-import--library--basic-develop--export)) and then implemented as this slice.

- **New module `app/src-tauri/src/preview_cache.rs`** owns disk-cache-generation concerns moved out of `lib.rs` (`DevelopPreviewInfo`, `DEVELOP_PREVIEW_MAX_DIMENSION`, `capped_dimensions`). Two entry points: `ensure_develop_preview(path, previews_dir)` (interactive — reads+hashes the file itself since the frontend only supplies a path) and `ensure_develop_preview_for_hash(path, hash, previews_dir)` (background-walk — skips the read+hash entirely on a cache hit, given an already-known hash from the catalog). Both are "ensure a cache entry exists" semantics, never force-regenerate.
- **Real correctness fix, not just a perf one**: the cached PNG's filename now comes from the source file's **content hash** (`blake3::hash(&bytes)`), not a hash of its path (Slice 3's original approach). The path-hash scheme had a latent bug — a file replaced in place with different bytes at the same path would have silently kept serving a stale cached preview forever. Content-hash keying also means a moved/renamed file with identical bytes resolves to the existing cache entry for free, which is a strict improvement on the PRD's own "regenerated when the source file changes (moved/re-imported/replaced)" phrasing.
- **`catalog.rs`**: `ImageSummary`/`list_images()` now expose `content_hash` (nullable, matching the DB column) — this is what makes the background walk cheap: it uses the hash already computed and stored at import time instead of re-reading+re-hashing every RAW file on every walk. (A design review from a Plan subagent caught this before implementation — the naive version, always reading+hashing regardless of the known hash, would have turned "cheap rescan" into O(catalog size in bytes) of disk I/O per import/startup.)
- **Two background triggers**, both calling `preview_cache::pregenerate_missing` (walks `list_images()`, sequential, skips-not-aborts on a per-image failure): after every `import_folder` call (fire-and-forget, doesn't delay the command's response), and once at app startup in `lib.rs`'s `.setup()` — the startup pass is what catches up images cataloged before this feature existed (the app's real catalog already had one such image from Slice 3 testing).
- **Deliberately sequential, not a worker pool** — avoids CPU/memory spikes decoding many RAW files at once. Accepted, explicitly-named tradeoff: with no priority queue, a large first-run backlog walk can transiently compete for CPU with an interactive Develop-open decode for whatever image the user just clicked into. Self-healing (worst case: one duplicate decode), not a blocker.
- **No frontend changes needed** — `DevelopCanvas.svelte`'s existing "Decoding…" overlay already covers every cache-miss case (first-ever open, background walk hasn't reached that image yet, app restarted mid-walk).
- **Verified empirically, not just via tests**: cleared the real `previews/` directory, relaunched the actual app with zero frontend interaction, and confirmed the startup catch-up pass regenerated `previews/{content_hash}.png` for the real cataloged image — filename matched the catalog's stored `content_hash` exactly. Relaunched a second time and confirmed the PNG's mtime was byte-for-byte unchanged (`Jul 26 11:47:22` both times), proving the second run hit the cache and did not redecode.
- `cargo test --lib`: 18/18 passing, including new real-file-gated tests in `preview_cache.rs` (cache-hit skips redecode, verified via unchanged mtime; identical content at two different paths resolves to the same cache entry; `pregenerate_missing` against a real `scan_and_import`'d catalog produces the expected cache file). `npm run check`: 0 errors, 0 warnings.

Worth remembering for future config-only changes (e.g. the `spike`/`spike-revert` Makefile targets), not fixed here since it's a dev-loop quirk, not a shipped-code bug.
