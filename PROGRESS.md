## Fix: thumbnail-regen/flush-save race hazard (2026-08-07)

User reported a photo's thumbnail seeming to go missing/not reflect an edit, while a separate Dehaze WGSL bug (fixed in the same session, see below) was independently confirmed as the actual cause of what they were seeing at the time (a broken Develop-canvas render, not a Library/Filmstrip thumbnail issue). While investigating, found a real, code-verified hazard worth fixing regardless: `openDevelop`, `switchModule`, and `handleExportClick` each fire `flushEditStack()` (writes the current edit stack to the catalog) immediately followed by `regenerateThumbnailFor()` (a separate IPC call whose own Rust command re-reads the edit stack fresh from the catalog, per its own doc comment) — WITHOUT awaiting the first call. Neither Tauri's own command dispatch nor the underlying SQLite write is guaranteed to land before the very next command's own read starts, so the regen could in principle read a stale, pre-edit stack.

- **Not independently confirmed as a reproduced user-visible symptom** — an attempt to reproduce one via the real running app was confounded by reusing an identical edit-stack value (the same Dehaze amount) across consecutive test runs, which correctly produces an identical, unchanged content-addressed thumbnail path regardless of ordering (a false alarm from the test's own methodology, not evidence of the race). Once corrected (a genuinely different value each run), the mechanism worked correctly even before this fix.
- **Fixed anyway, on precedent**: this is the same class of bug ("a write and a dependent read fired without awaiting the write") already found and fixed once this session for `flushEditStack()` itself (its own `persistTimer`-gated write, fixed as part of the Reset-button slice) — worth closing here too rather than leaving a real, if unconfirmed, hazard in place. All three call sites now `await flushEditStack()` before `regenerateThumbnailFor()`.
- `npm run check`: 0 errors/warnings. `cargo test --lib`: 103/103 passing (frontend-only change).

## Develop panel: "Reset" button (2026-08-05)

User asked to "add reset button to edit zone" — clarified via `AskUserQuestion` (whole-panel reset vs. per-Split-Toning-zone reset vs. per-section reset) that this means one button reverting **every** adjustment and mask on the current photo back to default in one shot, matching real Lightroom's own Develop-module Reset, not a scoped per-section reset.

- **Trivial by construction, once traced through the existing code**: `editStack` is `{schema_version, ops: []}` and every adjustment/tool/mask this app has is one entry in that same flat `ops` array. A full reset is just "clear `ops`, keep `schema_version`" (`resetEditStack`, new in `develop.js`) — every section's own getter (`getToneCurvePoints`, `getHslBands`, `opValue`, `listMasks`, …) already falls back to its own identity default when its op is absent, so nothing downstream needed new wiring; the reactive plumbing built for every prior slice handles it for free.
- **A real, pre-existing persistence bug found and fixed along the way, not just worked around.** The plan modeled the new handler on `handleMaskDeleted`'s existing shape (mutate `editStack`, then call `flushEditStack()` immediately, bypassing the usual 250ms slider debounce). Empirical verification against the real running app caught that this doesn't actually persist: `flushEditStack()`'s write was gated behind `if (persistTimer !== null)` — correct for every slider-driven caller (which always sets `persistTimer` via `setTimeout` right before a later flush), but silently wrong for any handler that mutates `editStack` directly and expects an immediate write, since neither `handleMaskDeleted` nor the new Reset handler ever sets that timer first. The first empirical pass showed the in-memory state correctly reset (`editStackAfterOps: 0`) while the catalog's real persisted row still had all 5 original ops (`persistedOps: 5`) — a genuine, verified defect, not a suspected one. **This means mask deletions had the same latent bug all along**: a deleted mask's removal was never actually written to the catalog unless some unrelated later slider edit happened to also flush before quitting, so a deleted mask could silently reappear after a full app quit and reopen. Fixed at the root: `flushEditStack()` now always persists the current stack whenever a Develop image is open, regardless of whether a timer happened to be pending — harmless (an idempotent re-write of unchanged data) for its other callers (`openDevelop`, `switchModule`, `handleExportClick`, all of which only ever call it when a timer legitimately might be pending), and correct for the two immediate-mutation callers that don't set one. Re-verified empirically after the fix: a second pass (triggered by Vite HMR reloading after the source edit) confirmed `persistedOps: 0` against the real catalog.
- **UI**: a small `.panel-header` row at the top of `DevelopPanel.svelte`, above "Basic" — "Edit" label + a "Reset" button, disabled when there's nothing to reset (`editStack.ops.length === 0`, avoiding a no-op confirmation dialog, the same guard shape the titlebar's own "Remove" button already uses). Gated behind the existing `ConfirmDialog.svelte` component (already used for "Remove from catalog," no changes needed to it) since this is destructive and can't be undone. Styled with the same destructive-action color this codebase already uses elsewhere (`MaskEditorPanel.svelte`'s `.delete` button, `ConfirmDialog.svelte`'s own `.danger` confirm button) rather than inventing a new visual language for "this is destructive."
- **Verified empirically through the real running app** (same `report_spike_result`-bridged harness technique used throughout this project, removed before commit), reusing the real catalog's own leftover multi-op test state (a luminance-range mask, a linear-gradient mask, exposure, HSL bands, and a tone-curve op — 5 ops total, genuine debris from earlier unrelated testing sessions, itself a real stand-in for "a photo with real edits"): confirmed the button starts disabled on first load's edit count check, becomes enabled once edits exist, clicking it opens the confirm dialog, confirming clears the in-memory edit stack to empty AND (after the fix above) the real persisted catalog row, resets `selectedMaskId`/`activeTool` to `null`, and every section's UI correctly falls back to its own identity default (tone curve back to the straight `[{0,0},{1,1}]` line, all 8 HSL bands back to zero). Catalog restored to its original pre-test state afterward.
- `npm run check`: 0 errors/warnings. `cargo test --lib`: 99/99 passing (no Rust changes; the fix was frontend-only, and every op this reset touches was already correctly handled by the Rust side for the "absent op" case, since that's the exact state a never-edited photo already produces).

## M3 — Split Toning (2026-08-05)

Next unbuilt M3 item after HSL / Color Mixer: classic split toning — a Shadows zone and a Highlights zone, each with an absolute tint Hue (0-360) and Saturation (0-100, tint strength), plus a shared Balance (-100..100) shifting where the shadow/highlight crossover sits in the tonal range (5 parameters total). Modern 3-zone Color Grading (adds Midtones + per-zone Luminance) is an explicit, named follow-up, not this slice. Slots in as the new final global-pass step: exposure → contrast → saturation → tone curve → HSL → **split toning**, still before masks (confirmed unchanged, zero mask-formula edits needed). Unlike Tone Curve/HSL, `DevelopPanel.svelte` had no placeholder for this — a genuinely new section, inserted right after "HSL / Color."

- **Design reviewed before implementation, and it caught a real bug before it was ever written.** My own draft approach applied the Shadow and Highlight tints as two *sequential* blends (shadow-then-highlight, or the reverse) — the review proved this is order-dependent (the result differs by a real cross term) whenever both zone weights are nonzero, which given this design's full-range smoothstep transition is true for nearly every pixel, not a rare edge case. Fixed with a single simultaneous 3-way convex combination instead (`rgb*(1-a_sh-a_hi) + tint_sh*a_sh + tint_hi*a_hi`), proven algebraically order-independent and overshoot-safe: since the two zone weights always sum to exactly 1 and both saturation terms are capped at 1, the three blend weights are provably non-negative and sum to exactly 1 — a genuine convex combination, no clamp needed. It also corrected my own framing on a real, easy-to-miss detail: **three** null-guard lists needed the new GPU buffer added, not two (`applyBitmapToGpu`, `loadImage`, and `writeAdjustmentsAndRender`, confirmed by direct grep) — the same class of miss the HSL slice's own review had already flagged once.
- **Reuses HSL's already-shipped `rgb_to_hsl`/`hsl_to_rgb` (Rust) and `rgbToHsl`/`hslToRgb` (WGSL) as-is** — no new color-space math needed. Zone weight is a smoothstep of the pixel's own lightness (`(max+min)/2`, the SAME lightness definition `hsl_to_rgb` requires as input to reconstruct color correctly — using perceptual luma here instead would be colorimetrically wrong, not just a stylistic difference), shifted by Balance: `t = clamp(l + balance/200, 0, 1); weight_highlights = smoothstep(0,1,t)`. Smoothstep (not a linear ramp) chosen for the same C¹-continuity reason HSL used raised-cosine over a triangular ramp — no slope-kink seam on a smooth luminance gradient.
- **A confirmed non-risk, named explicitly rather than reflexively porting over HSL's own mitigation**: HSL's `chroma_fade` term (suppressing hue-shift near gray, since hue is a ratio of near-equal RGB channels and therefore numerically unstable there) does NOT apply to this formula — split toning never reads a pixel's own hue or saturation, only its lightness, a simple, well-behaved computation with no division-by-small-delta anywhere. Porting `chroma_fade` over anyway would have actively *broken* the feature: tinting near-neutral shadow/highlight tones is split toning's entire purpose (classic teal-orange grading relies on exactly that).
- **A real, deliberate, checked property of the fixed-width transition, named rather than silently discovered later**: at `balance=±100`, the disfavored zone's weight never drops below 0.5 anywhere in `[0,1]` — the crossover midpoint simply sits at one endpoint of the transition. Not a bug; an accepted consequence of choosing a transition that spans the image's full tonal range rather than adding a 6th "width" parameter.
- **New WGSL `@binding(7)` — a dedicated named `struct SplitToning`, not a vec4-array like HSL's `hslBands`/the tone curve's `curveLut`**: 5 named scalars (shadow hue/saturation, highlight hue/saturation, balance) have no natural per-element repetition the way 8 bands or 256 samples do, so this mirrors the existing `Adjustments` struct's own style instead. Confirmed `Adjustments` itself has zero spare capacity for these (its 3 padding floats are alignment padding, not general room) before deciding a new binding was actually needed, not assumed.
- **`develop.js` gets a NESTED (not flat) data model** — `{op: "split_toning", shadows: {hue,saturation}, highlights: {hue,saturation}, balance}` — matching `upsertHslBand`'s own "patch one zone without touching the rest" access pattern, and chosen specifically so a later 3-zone Color Grading follow-up can add a `midtones` key additively rather than needing a flat-naming-scheme restructure.
- **UI**: two zone groups (Shadows, Highlights), each with a live color swatch computed directly from that zone's own current Hue/Saturation slider values (`hsl(hue, saturation%, 50%)`) — deliberately different from HSL's own swatch, which is tied to a *fixed* band-center constant (an identity marker, unrelated to that band's own shift-delta slider values). Split Toning's sliders ARE themselves an absolute color, so the swatch must track live values or it's simply wrong; at saturation=0 it correctly renders mid-gray regardless of hue, a free visual confirmation the zone is currently a no-op. The Hue slider deliberately uses a plain `0..360` unsigned display, NOT HSL's `+`/`-` signed-value idiom — a real, flagged-in-advance copy-paste risk when using the HSL row as a markup template, since Split Toning's Hue is an absolute tint-wheel position, not a relative shift.
- **Verified empirically through the real running app** (same `report_spike_result`-bridged harness technique used throughout this project, removed before commit): dragged the real Shadow Hue/Saturation sliders, confirmed the real persisted `split_toning` op via `getEditStack`; confirmed the WGSL pipeline renders without error with non-identity values active; ran a real export and pixel-sampled a genuinely dark region and a genuinely bright region of the real source photo against the true unedited source file — the dark region (lightness ≈0.15, shadow-weight ≈0.94) shifted strongly and warmly toward the orange shadow tint, while the bright region (lightness ≈0.80, shadow-weight ≈0.10) shifted only mildly, in exactly the proportion the formula predicts for each region's own computed weight — not a hard on/off cutoff, matching the design's own full-range smoothstep transition.
- `npm run check`: 0 errors/warnings. `cargo test --lib`: 103/103 passing (4 new hand-derived tests: zero-saturation passthrough regardless of hue/balance; a pure-shadow pixel isolating the Shadow zone; a pure-highlight pixel isolating the Highlight zone; and — the direct regression test for the sequential-blending bug the design review caught — a mid-gray pixel with both zones set to deliberately non-complementary hues and unequal saturations, script-verified that the correct simultaneous blend `(172,109,58)` differs by well outside tolerance from what an incorrect sequential blend of the identical inputs would produce `(163,118,67)`).

## M3 — HSL / Color Mixer (2026-08-04)

Next unbuilt M3 item after Tone Curve: 8 named color bands (Red, Orange, Yellow, Green, Aqua, Blue, Purple, Magenta), each with independent Hue/Saturation/Luminance sliders (24 parameters), where a pixel's own hue determines how much each band's adjustment applies — smoothly blended between adjacent bands, not a hard cutoff. The first genuinely new class of computation in this codebase: everything shipped so far (exposure/contrast/saturation, the tone curve's LUT) operates in plain RGB; this is the first real RGB↔HSL/hue-wheel math. Slots in as the new final step of the global pass: exposure → contrast → saturation → tone curve → **HSL**, still before masks (which read the post-global `rgb` as their own accumulator — confirmed unchanged, zero mask-formula edits needed).

- **Design reviewed before implementation**, specifically on the color-science formula (the highest-risk, most novel part). It verified directly against the real code (not assumed) that the existing `Adjustments` uniform struct has zero spare room for 24 new values (confirming a new WGSL binding is required), that no tab-widget precedent exists anywhere in this codebase, and that this project's zero-`svelte-ignore` a11y discipline still holds. It made one deliberate, justified departure from the just-shipped Tone Curve precedent: **no shared LUT this time** — the entire HSL formula is closed-form trig/arithmetic (mod, abs, cos, a few divides, a clamp) with no interpolation-method ambiguity to diverge on between WGSL and Rust, unlike the tone curve's genuinely shape-ambiguous monotonic spline; a LUT here would be unneeded complexity.
- **Standard HSL, not this codebase's own perceptual luma** — the HSL→RGB reconstruction is only mathematically valid for the lightness it was derived from (`(max+min)/2`); substituting the existing `dot(rgb, vec3(0.2126,0.7152,0.0722))` luma (used elsewhere for global Saturation and luminance-range-mask selection, an unrelated concern) would produce colorimetrically wrong output, not just a stylistic difference.
- **Band centers evenly spaced 45° apart starting at Red** (no verifiable source for Adobe's own internal angles, and this is a from-scratch reimplementation, not file-compatible with Lightroom) with a **raised-cosine blend weight** between adjacent bands — chosen over a triangular ramp specifically because it's C¹-continuous (no slope-kink seam at a band center on a continuous hue gradient like sky or skin). Centers being exactly 45° apart means at most 2 bands are ever active at once, and their weights sum to exactly 1 by the cosine identity `cos(x) + cos(π−x) = 0` — no gap, no double-count, no renormalization needed anywhere.
- **All 8 bands combine into one hue/saturation/luminance delta, applied once** (not 8 successive blends) — correct, not just cheaper, since at most 2 weights are ever nonzero. The hue-wraparound pitfall (naively averaging two angles straddling 0°/360°) is avoided entirely by combining **shift deltas**, not resultant angles, and wrapping only once on the summed delta.
- **A real, specific risk identified and given a load-bearing (not defensive) fix**: hue is derived from ratios/differences of near-equal RGB channel values — exactly where 8-bit source-texture quantization noise is largest relative to signal, i.e. in low-saturation regions (skies, skin, walls). Unlike every earlier adjustment (smooth remaps of an already-quantized input), HSL's hue-rotation is a genuinely new mechanism that could amplify that noise into visible mottling. Fixed with a `chroma_fade` term (`clamp(saturation / 0.08, 0, 1)`) that tapers hue-shift and luminance-delta application toward zero exactly where hue becomes numerically unreliable — algorithmic, not a higher-precision-texture architectural change. Also correctly handles achromatic pixels' mathematically-undefined hue (harmless for Saturation, which is naturally self-fading; would be visibly wrong for Luminance without the same fade).
- **New WGSL uniform** `@binding(6) hslBands: array<vec4<f32>, 8>` — one vec4 per band (hue/saturation/luminance/unused padding), device-scoped like `curveLutBuffer` (created once in `initGpu`, rewritten every render, never recreated per image). Both existing null-guard lists (`applyBitmapToGpu`'s and `writeAdjustmentsAndRender`'s) extended — the exact footgun the Tone Curve slice already flagged as easy to miss one of.
- **A WGSL-specific correctness fix, caught before it could ship silently wrong**: WGSL's `%` operator is truncated remainder (sign follows the dividend), not the always-non-negative floor-mod this hue-wraparound math needs — used a small `rem_euclid(a, b) = a - b*floor(a/b)` helper throughout the WGSL port to exactly match Rust's `f32::rem_euclid`, rather than assuming `%` behaves the same in both languages.
- **`develop.js` gets a band-KEYED (not flat-array) data model** — `{op: "hsl", bands: {red: {hue,saturation,luminance}, ...}}` — so a per-band UI control (`upsertHslBand(stack, bandName, patch)`) can patch exactly one band's values without threading the other 21 through, mirroring why masks needed their own CRUD instead of `opValue`/`upsertOp`'s scalar shape.
- **UI: flat per-band groups, no 3-tab (Hue/Saturation/Luminance) structure this slice** — real Lightroom's own HSL panel is 3 tabs over the same 8 bands, but no tab-widget precedent exists anywhere in this codebase, and building one purely for panel layout (not for any missing capability) would be new-pattern scope unjustified by this slice alone. All 8 bands × all 3 parameters genuinely work; only navigation/grouping differs from real Lightroom, matching this project's "smallest real instance first" discipline without cutting real functionality. Each band gets a small color swatch (`hsl(center, 70%, 50%)`, zero new math — the angle is already a shared constant) since "Aqua" vs. "Blue" vs. "Purple" are genuinely ambiguous by name alone.
- **Verified empirically through the real running app** (same `report_spike_result`-bridged harness technique used throughout this project, removed before commit): dragged the real Red band's Hue/Saturation/Luminance sliders, confirmed the real persisted `hsl` op via `getEditStack`; confirmed the WGSL pipeline renders without error with non-identity bands active; ran a real export and pixel-sampled two real regions of the source photo against the true unedited source file (not a downscaled preview, to avoid a resolution-mismatch confound) — a reddish-brown region (hue ~21°, near the Red/Orange boundary) shifted from `srgb(53,35,25)` to `srgb(141,106,52)` (a strong, correct shift matching the boosted Red band), while a yellow-green region (hue ~97°, well outside Red's influence) came back **byte-identical** to the unedited baseline, `srgb(133,147,124)` both before and after — clean, decisive proof of band isolation, not a global shift. One real confound caught and corrected along the way, not silently worked around: the first pass showed the "unaffected" region shifting too, traced to leftover `exposure`/mask ops from an earlier, unrelated session's own empirical testing still sitting in the real catalog (not something this slice introduced) — isolated by temporarily clearing those ops for a clean comparison, then restored to their original state afterward.
- `npm run check`: 0 errors/warnings. `cargo test --lib`: 99/99 passing (4 new hand-derived tests, expected values computed via script running the exact same formula: absent bands is an exact passthrough; a pixel exactly at a band's own hue center isolates that band completely; a boundary-hue pixel with opposite-signed neighboring-band luminance deltas proves a smooth blend rather than a hard nearest-band cutoff — the near-cancellation this test's specific values were chosen to produce would look very different under a cutoff bug; a near-gray pixel proves `chroma_fade` measurably suppresses the shift).

## M3 — Tone Curve: master RGB point curve (2026-08-04)

Next unbuilt M3 scope item after all mask work: "Tone curve, HSL/color mixer, split toning, dehaze, clarity/texture, vignette, grain" — scoped to Tone Curve only, matching this project's own "smallest real instance first" pattern and `DevelopPanel.svelte`'s own placeholder (`{ title: "Tone Curve", note: "Point curve editor" }`), which this slice replaces with a real implementation. A single master curve (applied identically to R/G/B, not separate per-channel tabs — a named follow-up) mapping input tonal value to output, edited by dragging points on a graph. Real Lightroom applies Tone Curve after Basic-panel exposure/contrast/saturation, before HSL — this app's simplified pipeline now runs exposure → contrast → saturation → **tone curve**, as a new final step in the existing global pass, before masks (which already read the post-global `rgb` as their accumulator base) layer on top.

- **Design reviewed before implementation, specifically on the one genuinely hard part**: the monotonic cubic interpolation algorithm. Chose Fritsch–Carlson (no overshoot/ringing between control points, unlike a naive natural cubic spline, which can produce visibly reversed-tone banding). The review wrote out the exact, correct 4-step algorithm precisely because one step (sign-zeroing a tangent at a local extremum, distinct from the later magnitude-only rescale step) is easy to omit and get subtly wrong — a plain averaged tangent can have the wrong *sign* at an extremum, which only that explicit zeroing step catches.
- **Parity mechanism: both the WGSL shader and `develop_engine.rs` build and consume the IDENTICAL 256-sample LUT**, not "Rust exact, shader approximate" — the latter would reintroduce a real near-extrema gap outside this module's existing `±2/255` test tolerance (established for ordinary float rounding, not for two structurally different evaluation methods). Both sides run the same Fritsch–Carlson tangent computation, sample at the same 256 points, and linearly interpolate between LUT entries the same way — parity by construction, not by luck. The curve-editor UI draws from this exact same LUT too, so what's shown always matches what's applied.
- **Shared math lives in `develop.js`** (`buildToneCurveLut`/`sampleCurveLut`, plus `getToneCurvePoints`/`upsertToneCurve` — a structured `{points: [{x,y}...]}` payload doesn't fit `opValue`/`upsertOp`'s scalar-value shape, the same reason masks needed their own CRUD helpers), consumed by both `DevelopCanvas.svelte` (GPU upload) and the new `ToneCurveEditor.svelte` (drawing).
- **New WGSL uniform** `@binding(5) curveLut: array<vec4<f32>, 64>` — packed as 64 vec4s (256 f32 samples), not `array<f32,256>`: WGSL's uniform-array stride must be a multiple of 16 bytes (the `Mask` struct's own comment already documents hitting this exact footgun once before). Device-scoped like `uniformBuffer`/`masksBuffer` (created once in `initGpu`, rewritten via `writeBuffer` on every render, never recreated per image) — unlike `sourceTexture`/`brushTextureArray`, which a curve's shape has nothing to do with.
- **`develop_engine.rs`** gets a hand-synced Rust port of the identical algorithm (`compute_tangents`/`hermite_at`/`build_curve_lut`/`sample_lut`), inserted into `apply_edit_stack` as the pipeline's new final global step, built once per call (not per pixel).
- **New `ToneCurveEditor.svelte`**: an SVG point-curve graph. Click empty space to add a point (rejected past `MAX_CURVE_POINTS=16`, and rejected within a minimum x-spacing of an existing point — a real, guarded-against divide-by-zero risk in the secant-slope computation both this component and the Rust/WGSL sides share); drag a point (endpoints locked to x=0/x=1, interior points clamped strictly between their neighbors so a drag can never cross/reorder points mid-gesture); double-click an interior point to delete it (endpoints are permanent anchors). Drag interaction mirrors `DevelopCanvas.svelte`'s existing mask-handle-drag ordering exactly — set drag state *before* calling `setPointerCapture`, wrapped in try/catch — since that specific ordering is a real, previously-hit bug in this exact class of interaction (a throw from `setPointerCapture` called first silently aborted everything after it), not a hypothetical worth re-deriving from scratch.
- **A real accessibility gap caught before shipping, fixed rather than suppressed**: `svelte-check`'s a11y lint flagged the graph's click-to-add background and the draggable points as mouse-only interactive elements with no keyboard path. This codebase's own established practice is a real fix, not a lint-suppressing comment (no `svelte-ignore` precedent exists anywhere in this codebase, confirmed by grep) — added `role`/`tabindex` plus real keyboard support: Enter/Space on the graph adds a point at the curve's own current midpoint value; Arrow Up/Down (Shift for a bigger step) nudge a focused point's y; Delete/Backspace removes an interior point, mirroring the mouse double-click.
- **Verified empirically through the real running app** (same `report_spike_result`-bridged harness technique used throughout this project, removed before commit): dispatched real `PointerEvent`s/`MouseEvent`s against the real `ToneCurveEditor` SVG, confirmed a real added point and a real dragged point both persisted correctly via `getEditStack` (a genuine test-timing bug in the harness itself was caught and fixed along the way — the first pass read back too early, before the existing 250ms persistence debounce had fired, and looked exactly like a real delete-not-working bug until the wait was extended past 250ms and the delete showed up correctly); confirmed the WGSL pipeline renders with no error overlay with a real non-identity 3-point curve active; confirmed adding points past `MAX_CURVE_POINTS` is silently capped at exactly 16, not runaway; confirmed double-clicking an interior point removes exactly one point and double-clicking an endpoint is correctly a no-op.
- **Not separately empirically re-verified via a live export**: the export path (`export.rs::export_one`) calls the exact same `develop_engine.rs::apply_edit_stack` function the new hand-derived Rust unit tests already exercise directly and exactly — that's the same code path, not an inference from a different one, so a live-app export pixel-check would have been redundant with what the unit tests already prove precisely.

## M3 — Range masking, part 2: color range mask (2026-08-03)

Second and last half of "Range masking: color range and luminance range selection" (PRD/MILESTONES.md), following the luminance-range slice (PR #31). That slice explicitly deferred color range, naming two real reasons: it needs a genuinely new click-to-sample-a-pixel-color interaction, and it needs an `ImageBitmap`-retention fix its own design review confirmed as real (`DevelopCanvas.svelte`'s decoded bitmap was discarded right after its one-time GPU-texture upload, with nothing keeping pixel data around for a future eyedropper to read).

- **Design reviewed before implementation, and it caught a real, would-have-shipped correctness bug** in the weight formula's first draft: at `range=0, feather=0` — the single most obvious "strict color match" setting a user would reach for — the formula evaluated to weight=0 even at the exact sampled pixel, because the `denom` floor meant to prevent divide-by-zero at `feather=0` also diluted the numerator's `feather_width` term. Fixed by reformulating so `denom` is the transition width added *after* the threshold (`weight = clamp((threshold - dist) / denom + 1.0, 0.0, 1.0)`), not blended into the numerator — `dist <= threshold` now always yields exactly 1 regardless of how small `denom` is. Packs into the *existing* 12-float `Mask` struct layout with zero new fields — `start_end.xyz` = refColor, `start_end.w` = range (linear and radial masks already use all four `start_end` slots too, so this isn't new territory for the struct). `Mask::weight`'s `rgb` parameter (added specifically for luminance range) is reused directly — no signature change needed, and order-dependency (a preceding mask's effect on `rgb` shifts what a later color-range mask selects) carries over for free, for the same already-documented WYSIWYG reason.

## M3 — Range masking, part 1: luminance range mask (2026-08-03)

Next unbuilt M3 scope item after the mask-overlay polish pass: "Range masking: color range and luminance range selection" (PRD/MILESTONES.md). Split into two slices, same way linear/radial split before it — this slice is luminance range only; color range (needing a genuinely new click-to-sample-a-pixel-color interaction) is a deliberate, named follow-up, not bundled in.

This is the **first mask kind whose weight depends on pixel VALUE (luminance) rather than pixel POSITION** — every earlier kind (linear/radial: pure geometry; brush: rasterized from geometry) computed weight from `uv`/`aspect` alone. Turns out architecturally simpler in one way (no new texture, no new geometry — the fragment shader already has `rgb` in scope before the mask loop even starts), but surfaces a genuinely new question (mask order now affects *what gets selected*, not just how it's graded) and forced two real, pre-existing latent bugs into the open.

- **Design reviewed before implementation, and it found two real, would-have-shipped bugs in the EXISTING code** (not just the new feature): the WGSL shader's mask-kind dispatch (`if params.z > 1.5 {brush} else if params.z < 0.5 {linear} else {radial}`) is a two-comparison threshold chain that only correctly bucketed kinds 0/1/2 by *coincidence* — a 4th kind would silently alias onto the brush branch, sampling a texture layer that was never assigned one. And the JS mask-packing loop's catch-all `else` (which assumed "anything that isn't radial or brush is linear") would throw a `TypeError` reading `m.start.x` on `undefined` the instant a luminance-range mask coexisted with any other kind, aborting the render for every mask in the stack, not just the new one. Both fixed: the WGSL dispatch became real ascending bands (ordered `if`/`else if` bounding one kind each, not overlapping thresholds); the JS loop gained an explicit branch per kind with no assumption-based catch-all.
- **New `luminance_range_mask` op**: `{id, rangeMin, rangeMax, feather, invert, exposure, contrast, saturation}`, `rangeMin`/`rangeMax`/`feather` stored 0-100 (matching linear/radial's own `feather` convention, not a separate 0-1 scale). Weight formula (verified independently by the review, same "raw expression, clamp exactly once" style as `mask_weight`/`radial_mask_weight`): `weight = clamp(min(rising, falling), 0, 1)` where `rising`/`falling` are the two UNCLAMPED slope expressions — taking `min()` before the single final clamp is what keeps this correct outside the range (a naive per-term-clamped version would incorrectly clamp a far-outside luma back toward 1 instead of 0). Packs into the *existing* 12-float `Mask` struct layout with zero new fields — even less new uniform surface than brush needed.
- **Mask order now affects selection, not just grading — named explicitly and given its own parity test**, not left implicit. Because luminance weight reads `rgb`, and `rgb` is a mutating accumulator in both the WGSL loop and `apply_edit_stack`'s Rust loop, a luminance-range mask's effective selection now depends on which masks precede it in the stack — the correct WYSIWYG behavior (select pixels as currently graded), a genuinely new category of interaction no earlier mask kind had. `Mask::weight`'s Rust signature grew from `(&self, uv, aspect)` to `(&self, uv, aspect, rgb)` to support this.
- **The mask-overlay mechanism from the prior slice was unified, not duplicated a second time**: instead of building a separate overlay path for luminance range (no texture to sample — its weight is analytic), the brush-only `overlay_layer`/`overlay_invert` uniform pair was replaced with a single `selected_mask_index`, and the overlay blend moved *inside* the main per-mask loop, reusing each mask's own already-computed, already-inverted `weight` — gated to `kind > 1.5` (brush and luminance range) so linear/radial correctly keep their prior dashed-outline-only scope. This is a real simplification (less code, no separate re-sample-and-re-invert step) that also means any future no-geometry mask kind gets overlay support for free. `showBrushOverlay` renamed to `showMaskOverlay` throughout to match its now-general scope; a new `OVERLAY_CAPABLE_MASK_OPS` allowlist in `develop.js` is the single place this list lives (hotkey gate + checkbox gate can't drift apart).
- **UI**: luminance range creates immediately on tool-button click, with **no canvas interaction at all** — a real, deliberate divergence from every other mask kind (it has no geometry to place, matching real Lightroom's own behavior for this tool). ## M3 Slice 7 — Local adjustments: adjustment brush (2026-08-02)

Third and last named local-adjustment mask type, reusing the masking infrastructure the two gradient mask slices built. The biggest technical departure of the three: a brush stroke is a variable-length sequence of paint "dabs," not a single small parametric shape, so it can't reuse the fixed-size uniform-array-of-analytic-formulas approach linear/radial share. Auto-mask (edge-aware painting, a real image-segmentation feature) is deliberately deferred to a future slice — consistent with how this same MILESTONES.md bullet was already split once before (linear shipped before radial).

- **New `brush_mask` op**: `{id, dabs: [{x, y, radius, hardness, flow, mode: "add"|"erase"}], invert, exposure, contrast, saturation}` — no mask-level `feather` (unlike linear/radial): softness is baked per-dab at paint time from the brush tool's own Size/Feather/Flow settings, matching real Lightroom's own brush-options model (they apply to whatever gets painted *next*, not editable globally after the fact). `radius` is a normalized fraction of image WIDTH only (a single scalar) — deliberately, since rasterization happens directly in an offscreen canvas sized to the image's own native pixel resolution, where a single `radius * nativeWidth` used for both dimensions of `ctx.arc()` is inherently a true circle with no separate axis scaling needed (simpler than radial's `radiusX`/`radiusY`, which has to correct for aspect ratio because that geometry is evaluated analytically in normalized UV space).
- **A real, deliberate design divergence from linear/radial, named explicitly**: a brush mask can span *multiple separate strokes* (paint, lift the pointer, paint again, all adding to the same mask), matching real Lightroom's actual model, rather than linear/radial's "one placement = one mask." Implemented with zero new persistent cross-stroke state: every `pointerdown` re-derives the paint target fresh from `selectedMaskId` — if it currently points at a brush mask, the stroke appends to it; otherwise a new mask is created and selected. A "New Brush" tool-strip button achieves "start fresh" simply by deselecting (`selectedMaskId = null`), reusing the exact same re-derivation logic rather than a parallel reset signal.
- **Rasterization**: each active brush mask owns a persistent `OffscreenCanvas` (sized to the image's native resolution, opaque-black-initialized — not the canvas default transparent, which is required for `"multiply"` erase compositing to correctly no-op over never-painted areas, see below) that is **never cleared** — only newly-added dabs are drawn onto it each `pointermove`, keeping per-move cost bound by texture resolution/upload cost, not stroke length (a long stroke's full dab list is never re-rendered from scratch). Uploaded via `device.queue.writeTexture` into a `texture_2d_array` (one layer per active brush mask, sized to the same combined `MAX_MASKS`=8 budget every mask kind shares — a single shared texture would have silently broken true op-order interleaving and independent per-mask adjustments the moment there's more than one brush mask), indexed via the WGSL `Mask` struct's previously-unused `params.w` slot. Sampled via `textureSampleLevel` (not `textureSample`) since it sits inside a per-mask branch and has no implicit-derivative uniformity restriction to worry about.
- **Add vs. erase compositing, and a real correctness bug caught and fixed before it shipped**: add dabs use `"lighter"` (additive, clamped at full weight — matches real flow/density build-up, confirmed as the deliberately *additive*, not max-union, model, since two overlapping partial-flow dabs should build toward full coverage); erase dabs use `"multiply"` with a gradient from `(1-flow)` at the dab's center to `1.0` at its edge. The bug: a fresh `OffscreenCanvas` defaults to fully *transparent*, and Porter-Duff `"multiply"` against a transparent destination lets the erase gradient's own color show through directly (no destination alpha to constrain it) — meaning an erase stroke over an area that was never painted would incorrectly *paint* weight into it instead of correctly staying a no-op. Fixed by initializing every new canvas to opaque black before any dab is drawn, so `multiply`'s simplified opaque-vs-opaque formula (`Co = Cs × Cd`) correctly yields 0 regardless of the erase color wherever nothing has been painted yet. Caught during implementation by reasoning through the exact Porter-Duff composite math, not discovered empirically.
- **CPU parity (`develop_engine.rs`)**: a `Mask::Brush` variant with the identical per-dab accumulation formula — `add` dabs: `weight = (weight + falloff).min(1.0)`; `erase` dabs: `weight *= 1.0 - falloff` — the exact multiplicative reduction the canvas's own `"multiply"` composite produces, confirmed matching so both renderers agree. `aspect` (image height/width) threads through `Mask::weight` to reconstruct the same true-circle-in-pixel-space behavior the offscreen canvas gets "for free," since this CPU path has no canvas to rasterize into.
- **UI**: `MaskToolStrip.svelte` gained a Brush tool button, Size/Feather/Flow sliders (Feather shown is `100 - hardness`, matching the app's existing gradient-mask "Feather" convention even though the underlying `Dab` field is named `hardness`), an Erase toggle, and a "New Brush" button, plus a third independent per-kind chip counter ("Brush N"). `MaskEditorPanel.svelte` got a **real** third branch (not a free ride, per design review before implementation) — brush masks show Exposure/Contrast/Saturation/Invert/Delete but no Feather row, since softness is baked per-dab, not mask-level. `DevelopCanvas.svelte` shows a live circular brush-size cursor (aspect-corrected the same way the radial mask's on-screen-circle drag already is) that follows the pointer on hover, not just while painting. A fast drag interpolates intermediate dabs (spaced ~25% of the brush radius apart) so a stroke doesn't come out gappy/dotted.
- **Verified empirically through the real running app** (throwaway test harness temporarily added to `+page.svelte`'s `onMount`, removed before commit — real dispatched `PointerEvent`s against the real rendered canvas, real IPC round-trips through `flushEditStack`/`getEditStack`/`export_images` against the real persisted catalog; reported back via the existing `report_spike_result` Tauri command printing to the terminal running `cargo run`, since this app has no way to screenshot its native window and WKWebView's own console isn't forwarded there): a multi-point stroke produced correctly-interpolated, correctly-ordered dabs in the real catalog; a second stroke with no deselect appended to the *same* mask (multi-stroke-per-mask confirmed); clicking "New Brush" then painting created a genuinely separate second mask; toggling Erase and painting appended a dab with `mode:"erase"`; `canvas.width`/`canvas.height` correctly reflected the decoded image's real dimensions after load with no error overlay present, confirming the WGSL pipeline (including the new texture array and its bind-group entry) initialized without throwing — and again after switching to a second, different image and back, confirming the brush texture array and its rasterization state correctly reset and re-populated per image; a real export (via `develop_engine.rs`'s CPU path, the same code the new unit tests cover) with a +3EV boost on the painted mask produced `srgb(163,211,249)` → `srgb(255,255,255)` at a painted point and a byte-identical `srgb(166,140,113)` → `srgb(166,140,113)` at an untouched corner — real, visible, correctly-scoped proof of the effect, not just a claim that the command succeeded.
- `npm run check`: 0 errors/warnings. `cargo test --lib`: 80/80 passing (5 new brush parity cases: center dab, exact-radius-boundary exclusion, outside-every-dab, overlapping add dabs union additively not via max, and an erase dab reducing weight multiplicatively — each hand-computed before writing the assertion, same discipline as every prior mask slice).

## M3 Slice 3 — Develop pan/zoom & basic view controls (2026-07-30)

Third of M3's front-loaded scope additions. Develop's canvas was fit-to-window only — the entire "fit" mechanism was a bare `max-width/max-height:100%` CSS rule on the `<canvas>` in `DevelopCanvas.svelte`, no zoom-level state, no pan anywhere. Added Fit, 100% (true 1:1 canvas-backing-store pixels), zoom-to-point (click the image to toggle, centered on the click), and click-drag pan while zoomed — all self-contained in `DevelopCanvas.svelte`, no new props, no backend changes.

- **Real bug found and fixed by design review before implementation, not by testing**: the existing `.canvas-wrap`'s `align-items:center; justify-content:center` flex centering is a classic "scroll trap" once the canvas overflows in 100% mode — centering an overflowing flex item computes a negative starting scroll offset that clamps to 0, permanently hiding the "before center" portion of the image on *both* axes (no explicit `flex-direction` means `row`, so both centering properties are affected). Fixed with `margin: auto` on the canvas itself instead of centering the flex container — per the flexbox spec, auto margins absorb free space when the item fits (identical look to the old Fit behavior) and resolve to `0` when it overflows (normal, fully scrollable, no trap). One CSS rule correctly handles both modes.
- **Pan reuses native browser scroll clamping instead of hand-rolled math**: in 100% mode, `.canvas-wrap` becomes a real `overflow:auto` scroll container and the canvas renders at its true intrinsic size; drag-to-pan just writes `scrollLeft`/`scrollTop` directly from pointer deltas — the browser clamps to `[0, scrollWidth - clientWidth]` automatically, no manual bounds-checking needed.
- Click vs. drag disambiguation via a 4px movement threshold on `pointerup`; `canvasEl.setPointerCapture`/`releasePointerCapture` so a fast drag exiting the canvas near an edge doesn't stop delivering `pointermove`; `touch-action:none` on the canvas so native touch-scrolling doesn't fight the JS-driven scroll writes.
- Zoom-to-point converts the click's CSS-pixel position to a native canvas-backing-store coordinate using **per-axis** scale factors (`getBoundingClientRect()` width/height ratios computed separately, not one shared ratio — fractional CSS-pixel rounding can differ slightly per axis even though aspect ratio is preserved), then centers the viewport on it after `await tick()` (required: Svelte 5 runes still batch `$state`-triggered DOM patches to a microtask, so reading post-zoom layout synchronously would see stale dimensions).
- Small "Fit"/"100%" badge in the canvas corner, also clickable — discoverability beyond click-on-image.
- Zoom state resets to `"fit"` whenever the open image changes (a pure view concern, not persisted).
- Named, accepted limitation: "100%" is one canvas backing-store pixel per CSS pixel, not per physical device pixel — on HiDPI this looks ~2x more zoomed than true 1:1 physical pixels. Matches the component's existing intrinsic-sizing behavior already in place for Fit, not a new inconsistency introduced here.
- **Verified empirically through the real running app** (throwaway query-param-gated test driver temporarily added to the real `+page.svelte`, removed before commit — real dispatched `Pointer`/`MouseEvent`s against the real rendered canvas, not handler functions called directly): confirmed Fit renders at the expected downscaled size (811×608 against a 2048×1536 native preview) with the "zoomed" class absent; clicking the zoom badge engages 100% mode with the canvas's rendered CSS size exactly equal to its native backing-store size; **the scroll-trap fix specifically verified** by forcing scroll to both `(0,0)` and `(scrollWidth-clientWidth, scrollHeight-clientHeight)` and confirming both are reachable (the axis the review flagged as previously unreachable under naive flex centering); overshoot past either edge (both positive and negative) confirmed clamped by the browser, not the app; a real drag-panning sequence via dispatched `PointerEvent`s moved `scrollLeft`/`scrollTop` by exactly the expected delta; clicking the badge again returned to Fit with the display size restored exactly to its original value.

## M2 final slice — Catalog backup (2026-07-29)

Last remaining item on M2's scope list, resumed after being deliberately reprioritized behind the thumbnail-refresh/Filmstrip work above. Per PRD §7.6: prompt on app close with a configurable frequency (every time/daily/weekly/monthly/never), write a timestamped copy of the catalog file to a user-chosen folder kept separate from the working catalog, with an optional integrity check and optional vacuum/compact. Catalog file only — photos are never touched.

Planned via a reviewed design doc. The review corrected the design's central architectural premise: reading Tauri's actual shipped `onCloseRequested` implementation (`node_modules/@tauri-apps/api/window.js`) showed `event.preventDefault()` calling *after* an `await` is Tauri's own documented pattern, not something to engineer around — this eliminated an entire layer of planned startup-snapshot machinery in favor of just re-fetching settings fresh at the top of the close handler. It also flagged a real, deliberately-accepted mutex-hold-duration tradeoff, corrected the first-run default (a `never`-by-default would have made the feature permanently unreachable, since the close-prompt dialog is the *only* place backup settings can ever be changed), and confirmed `rusqlite::backup::Backup` against a WAL-mode source needs no manual checkpoint.

- **New `settings` key/value table**, greenfield — no settings/preferences storage existed anywhere in this codebase before this. `migrate()` inserts idempotent defaults (`backup_frequency: "weekly"`, not `"never"` — see above) on every `open()`, matching this project's existing "not a real migration system, but real enough" precedent.
- **`Catalog::perform_backup`**: canonicalizes and rejects a destination that's the same as or nested inside the app's own data folder (PRD explicitly requires "kept separate," not just a UI hint); runs `PRAGMA integrity_check` first if requested and refuses to write a backup of data already known to be corrupt; runs `VACUUM` if requested; copies via `rusqlite::backup::Backup` — SQLite's real Online Backup API, walking the source's pager rather than raw file bytes, the WAL-safe way to copy a live database without a manual checkpoint step.
- **Real bug found and fixed during empirical verification, not caught by any unit test**: the Online Backup API copies the source's pages verbatim, *including the header byte that records journal mode* — so a backup taken from this app's live WAL-mode catalog came out flagged as WAL-mode too. Confirmed on disk: opening the freshly-written backup file (even just to inspect it with the `sqlite3` CLI) spawned its own `-shm`/`-wal` sidecar files next to it, which is exactly wrong for what's supposed to be one portable, restorable artifact. Fixed by converting the destination connection to `journal_mode=DELETE` immediately after the backup completes — this checkpoints any residual WAL content into the main file and flips the header, confirmed by both a new unit test asserting `journal_mode` is `"delete"` on the finished copy, and by re-running the real smoke test and confirming no sidecar files appeared even after querying the file directly.
- **Deliberate, named exception to this codebase's own "release the mutex before slow work" convention** (`export_images`'s existing precedent): `perform_backup` holds `AppState.catalog`'s lock for its entire duration (integrity check + optional VACUUM + file copy), rather than releasing it before the slow part. Accepted because this is only reachable once, from the close-prompt dialog, immediately before the window is destroyed — documented in a comment matching `export_images`'s own style rather than silently deviating.
- **New `BackupPromptDialog.svelte`** serves both "configure" and "perform" at once, matching real Lightroom's own on-close-only prompt (no persistent settings screen exists anywhere in this app to host anything else). The close handler needed a genuinely new pattern for this codebase: every prior dialog is fire-and-forget from its caller's perspective, but this one needs the close handler to actually *wait* for the user's choice before destroying the window — a small promise-bridge (`showBackupPromptAndWait`/`resolveBackupPrompt`) does that, and "Skip This Time" is always available even if "Back Up Now" fails, so the wait can never trap the user unable to quit.
- **A real bug in my own throwaway verification script, not the shipped code**: the first empirical-verification attempt silently produced no result at all — the smoke test's close sequence called `unlisten()` (copied from the M1 Slice 6 smoke test's precedent) immediately before `getCurrentWindow().close()`, which unregistered the close handler *before* the close event fired, so the window just destroyed itself with zero interception. Root-caused by checking `ps aux` (the process had already exited with no report ever printed) rather than assuming the marker-wait command was still running; fixed by not unlistening before the actual close call.
- **Verified empirically through the real running app**, both branches: forced a stale `last_backup_at` via `sqlite3` on the real dev catalog, drove a real close through the actual `+page.svelte` close handler and the actual `BackupPromptDialog` component (via a throwaway smoke route, script-dispatching a real `MouseEvent` click on the real rendered button, same technique used for the Filmstrip slice above), and confirmed for **Back Up Now**: a real, valid, independently-openable backup file landed at the chosen folder (`PRAGMA integrity_check` → `ok`, correct row data, `journal_mode` → `delete`), and `last_backup_at` updated to the real completion time in the actual catalog; and for **Skip This Time**: no backup file was written, but `last_backup_at` still advanced (so skipping doesn't re-prompt on literally the next close). Smoke route and `tauri.conf.json`'s temporary window-`url` override were removed afterward; the real dev catalog's `settings` rows were reset to fresh defaults rather than left with test-session values.
- `cargo test --lib`: 61/61 passing (5 new: settings round-trip + idempotent defaults, a real on-disk backup that stays independently-openable and keeps `journal_mode=wal` on the *source* while landing `journal_mode=delete` on the *copy*, the destination-not-separate guard, and integrity-check blocking a deliberately corrupted catalog). `npm run check`: 0 errors, 0 warnings.
- **Deliberately deferred, named not silently dropped**: a manual "Back Up Now" trigger outside the close prompt, and any in-app restore UI — no menu/settings surface exists anywhere in this app yet to host either, and PRD's literal ask is prompt-on-close; recovery means pointing the app at a different catalog file, which needs no new UI (matches how real Lightroom itself handles this too).

## Bug fix: JPEG thumbnails stayed blank forever after import (2026-07-27)

User report, tested and root-caused rather than assumed. Symptom: after importing a JPEG, its Library grid cell stayed a blank placeholder indefinitely, even well after import finished.

- **Metadata was not actually broken** — checked first since the user's report bundled it with the thumbnail symptom. Ran the real extraction path against a real Sony NEX-6 JPEG (copied from a real photo on this machine, not synthetic) both directly (`extract_from_jpeg`) and through the full `import_files` → catalog round trip: camera/lens/exposure/captured-at all landed correctly and immediately. Cell selection wiring (`GridCell` → `LibraryGrid` → `selectedId` → `MetadataPanel`) was also confirmed correct by inspection. Most likely explanation for "no metadata" in the original report: the same blank-looking cell probably discouraged clicking into it, or the user's own test JPEG genuinely had no EXIF (common for downloaded/screenshotted images) — not a code bug.
- **The thumbnail symptom was real, and root-caused, not just patched around.** JPEG thumbnail generation is a fire-and-forget background pass (`import::generate_missing_thumbnails`, M2 Slice 1) that runs *after* the import command already returned its response — by design, so a JPEG-heavy import doesn't block on it. But `+page.svelte` only ever calls `refresh()` (→ `listImages()`) once, right after import (and once more at startup) — nothing ever told it to look again once the background pass actually finished. So the frontend's one-shot snapshot permanently showed `thumbnail_path: null` for the rest of the session, regardless of how long the background pass took or whether it succeeded.
- **Confirmed via a real reproduction, not just code reading**: imported a real 8MB/4000×2658 JPEG through the actual `import_files` command inside the running app, captured the frontend's `images` state immediately after import (thumbnail_path: null, as expected) and again via a direct backend query 4s later (still null) — proving the staleness wasn't just theoretical. A follow-up direct-Rust timing test found the actual cause of *that specific* run's failure: in this project's unoptimized dev build, decoding+resizing a real photo this size took **4.83s**, longer than the 4s window before the app closed — the background `spawn_blocking` task gets abandoned along with the process on quit, so a thumbnail generation that hasn't finished by the time the app closes is lost until the next startup catch-up pass. (Release builds should be dramatically faster since JPEG decode is CPU-bound and debug/dev builds are unoptimized — but the underlying staleness bug would still show up as a delay-then-never-updates symptom in *any* build, just a shorter delay.)
- **Fix**: `+page.svelte` gained `pollUntilThumbnailsReady()` — after any `refresh()` that could have left `thumbnail_path: null` rows (post-import, and the initial startup refresh, which races the app's own startup catch-up pass the same way), it polls `listImages()` every 1.5s (capped at 10 attempts, ~15s total) until no currently-tracked image has a null thumbnail. Bounded deliberately — a genuinely-failed decode (a real, permanent error) shouldn't poll forever; it just stops and leaves the placeholder, which is the correct outcome in that case.
- **Verified the fix actually works, not just that it compiles**: re-ran the same real-photo import through the running app, this time letting `runImport`'s own new polling logic run for real (not artificially closing early) — the frontend's own `images` state went from `thumbnail_path: null` immediately after import to the real generated thumbnail path ~4–8s later, entirely on its own, no manual refresh or restart needed.
- `cargo test --lib`: 42/42 passing (no test changes needed — this was a frontend-only fix, the backend's background-generation behavior was already correct and already covered).

## M1 Slice 6 — Crash-safety hardening + dogfood pass (final M1 slice): DONE (2026-07-26)

Exists to satisfy M1's own exit criteria: "No data loss across app restarts or crashes mid-edit," and "this is the first installable, dogfoodable build." Planned via a reviewed design doc — the review caught a bug that would have silently defeated the flagship fix before any code was written, and one real gap not in the original scope.

- **`flushEditStack()` in `+page.svelte` didn't return its write promise** — every `await flushEditStack()` call site (three existed already: `switchModule`, `openDevelop`, Slice 5's `handleExportClick`) resolved on the next microtask regardless of whether the actual `set_edit_stack` IPC call had landed. Fixed to return the real promise, and to track an in-flight `pendingSave` separately from the debounce timer (a second flush/close can happen while a previous flush's write is still resolving). This was the load-bearing fix everything else in this slice depended on.
- **New: flush the pending edit before the window actually closes.** `getCurrentWindow().onCloseRequested` intercepts a graceful quit, flushes (now correctly awaited), then `destroy()`s. **Named limitation, not hidden**: this protects a graceful quit only (close-button click, or another OS "please close" request routed through the same pipeline `.close()` itself uses per Tauri's own docs) — it cannot help against SIGKILL/a hard crash, which bypasses every in-process handler. Whether macOS Cmd+Q routes through this same path is unverified in this environment.
- **Real capability gap found and fixed along the way**: the app's `capabilities/default.json` only granted `core:default`, which does **not** include `core:window:allow-close`/`allow-destroy`. Without these, the new close-flush handler would have called `event.preventDefault()` and then failed to actually close the window — a user could have gotten **stuck unable to quit the app at all** after dragging a slider, which is arguably worse than the original data-loss bug. Found empirically (the first close-flush smoke-test run failed with `"window.close not allowed"`), not by code review — confirms the value of actually running this rather than assuming Tauri's default permissions were sufficient.
- **Import's two-row insert made atomic**: `import.rs` used to call `add_image_with_metadata` then a separate `add_edit_stack` — two independent auto-commit statements. New `Catalog::add_image_with_edit_stack` (`catalog.rs`) wraps both in one `unchecked_transaction`. Per the design review: a crash between the two old statements left an `images` row `list_images()` silently excluded (no matching `image_versions` row) but that `find_by_hash` still matched on every future import scan — the file became **permanently unimportable** through the normal UI, a disproportionately bad failure mode for how narrow the window was. Fixed by inspection (transactions are correct-by-construction), not by empirically reproducing the microsecond-scale race — padding an import with duplicate-content files to "widen" the window was considered and correctly rejected by the review as not actually testing what it would claim to.
- **SQLite hardened**: WAL mode + `synchronous=NORMAL` on `Catalog::open` (not `open_in_memory`). **Honest framing, not oversold**: the prior default (rollback journal + SQLite's own implicit `synchronous=FULL`) was already durable against process crashes — this doesn't close an existing hole in the "no data loss" criterion (the two fixes above do that). What it actually buys today is more forward-looking hygiene than a realized fix, since `AppState.catalog` is a single `Arc<Mutex<Catalog>>` around one connection — everything already serializes through Rust's own Mutex regardless of journal mode. Cheap and standard to add regardless. Used `pragma_update_and_check` (not `pragma_update`) specifically for `journal_mode`, since `pragma_update` silently swallows the row SQLite returns for that particular pragma and would "succeed" even if WAL failed to engage.
- **Verified empirically, not just by code review** (three real tests through the actual app, no tool to click/screenshot the native window so script-driven triggers substitute for physical interaction, same pattern used throughout this project):
  1. A throwaway `/m1-slice6-smoke` route scheduled a real debounced edit-stack write, then called the real `getCurrentWindow().close()` ~10ms later (well inside the 250ms debounce window) — the close-flush handler intercepted it, and after the process fully exited, `sqlite3` confirmed the edit landed (`exposure: 0.42`, the scheduled value) and WAL mode was active (`-wal`/`-shm` files present, `PRAGMA journal_mode` reports `wal`).
  2. `kill -9` against a running instance with only already-persisted state: `PRAGMA integrity_check` returned `ok` afterward, row counts and edit-stack content were unchanged — confirms the baseline persisted-write path was never the risky part.
  3. `kill -9` timed against a real `import_folder` call (via a throwaway `/m1-slice6-import-kill-smoke` route): the import (only 1-2 real files available in this environment, see below) completed before the kill landed in both attempts — this environment's real files process too fast to reliably land a kill inside the transaction window via external shell-script timing, which is itself consistent with the atomic fix making that window very small. `PRAGMA integrity_check` was `ok` afterward regardless.
- **Real dogfood pass, honestly scaled**: the actual M1 workflow (import → cull → develop → export) was exercised end-to-end across every slice's own verification this session, using this environment's 2 real CC0 sample RAW files — not PRD's literal "hundreds of RAW files" scale, which no larger real RAW set is available here to test. Named plainly rather than implied as tested at scale.
- `cargo test --lib`: 25/25 passing (new `add_image_with_edit_stack_inserts_both_rows_atomically` test). `npm run check`: 0 errors, 0 warnings.

**New named, deferred risks** (this slice's job is naming crash-safety gaps honestly, not fixing every one immediately):
- **`std::sync::Mutex` poisoning**: every catalog command does `state.catalog.lock().map_err(...)?`, and `catalog.rs` uses `.expect(...)` on EditStack JSON (de)serialization. A panic while the lock is held would poison it permanently for the process's lifetime — every later catalog call fails until the user force-quits and restarts. Low-probability today (nothing currently writes invalid JSON), not fixed this slice.
- **A truncated preview PNG from a crash mid-write during background pregeneration would be cached as permanently broken**: `ensure_develop_preview_for_hash`'s cache-hit check (`preview_cache.rs`) is just `out_path.exists()` — a partial file from an interrupted write would pass that check forever, then fail `image::image_dimensions` on every subsequent attempt, with no automatic retry/regeneration. Found while designing (not empirically reproducing) the pregeneration-kill test above. Lower severity than the catalog-side fixes in this slice (affects one cached preview file, not the catalog or the original RAW file — recoverable by deleting the one bad cache file), not fixed this slice.

## M1 Slice 4 — Develop preview cache: DONE (2026-07-26)

Slice 3 shipped Develop decoding the source RAW fresh on every open (explicitly deferred as "correct, simple; caching is a later optimization not a correctness requirement"). In practice this was slow enough that the user asked for a Lightroom-style pre-generated preview mechanism, which was first folded into the roadmap ([PRD §7.2](PRD/PRD.md#72-import)/[§7.6](PRD/PRD.md#76-performance--data-integrity-cross-cutting-not-a-feature-but-a-requirement), [MILESTONES.md's M1 section](PRD/MILESTONES.md#m1--mvp-import--library--basic-develop--export)) and then implemented as this slice.

- **New module `app/src-tauri/src/preview_cache.rs`** owns disk-cache-generation concerns moved out of `lib.rs` (`DevelopPreviewInfo`, `DEVELOP_PREVIEW_MAX_DIMENSION`, `capped_dimensions`). Two entry points: `ensure_develop_preview(path, previews_dir)` (interactive — reads+hashes the file itself since the frontend only supplies a path) and `ensure_develop_preview_for_hash(path, hash, previews_dir)` (background-walk — skips the read+hash entirely on a cache hit, given an already-known hash from the catalog). Both are "ensure a cache entry exists" semantics, never force-regenerate.
- **Real correctness fix, not just a perf one**: the cached PNG's filename now comes from the source file's **content hash** (`blake3::hash(&bytes)`), not a hash of its path (Slice 3's original approach). The path-hash scheme had a latent bug — a file replaced in place with different bytes at the same path would have silently kept serving a stale cached preview forever. Content-hash keying also means a moved/renamed file with identical bytes resolves to the existing cache entry for free, which is a strict improvement on the PRD's own "regenerated when the source file changes (moved/re-imported/replaced)" phrasing.
- **`catalog.rs`**: `ImageSummary`/`list_images()` now expose `content_hash` (nullable, matching the DB column) — this is what makes the background walk cheap: it uses the hash already computed and stored at import time instead of re-reading+re-hashing every RAW file on every walk. (A design review from a Plan subagent caught this before implementation — the naive version, always reading+hashing regardless of the known hash, would have turned "cheap rescan" into O(catalog size in bytes) of disk I/O per import/startup.)
- **Two background triggers**, both calling `preview_cache::pregenerate_missing` (walks `list_images()`, sequential, skips-not-aborts on a per-image failure): after every `import_folder` call (fire-and-forget, doesn't delay the command's response), and once at app startup in `lib.rs`'s `.setup()` — the startup pass is what catches up images cataloged before this feature existed (the app's real catalog already had one such image from Slice 3 testing).
- **Deliberately sequential, not a worker pool** — avoids CPU/memory spikes decoding many RAW files at once. Accepted, explicitly-named tradeoff: with no priority queue, a large first-run backlog walk can transiently compete for CPU with an interactive Develop-open decode for whatever image the user just clicked into. Self-healing (worst case: one duplicate decode), not a blocker.
- **No frontend changes needed** — `DevelopCanvas.svelte`'s existing "Decoding…" overlay already covers every cache-miss case (first-ever open, background walk hasn't reached that image yet, app restarted mid-walk).
- **Verified empirically, not just via tests**: cleared the real `previews/` directory, relaunched the actual app with zero frontend interaction, and confirmed the startup catch-up pass regenerated `previews/{content_hash}.png` for the real cataloged image — filename matched the catalog's stored `content_hash` exactly. Relaunched a second time and confirmed the PNG's mtime was byte-for-byte unchanged (`Jul 26 11:47:22` both times), proving the second run hit the cache and did not redecode.
- `cargo test --lib`: 18/18 passing, including new real-file-gated tests in `preview_cache.rs` (cache-hit skips redecode, verified via unchanged mtime; identical content at two different paths resolves to the same cache entry; `pregenerate_missing` against a real `scan_and_import`'d catalog produces the expected cache file). `npm run check`: 0 errors, 0 warnings.

- **Hand-rolled virtualized grid** (`src/lib/components/LibraryGrid.svelte`): computes visible row range from scroll position against a uniform grid layout, renders only visible rows + a 3-row buffer — no virtualization library, per UX-DESIGN.md §5's DOM-cost requirement. `GridCell.svelte` shows the thumbnail plus a hover-visible badge row (star rating, pick/reject flags, color-label dot), each wired to `set_rating`/`set_flag`/`set_color_label` with optimistic local UI updates.
- **Two real bugs caught by `npm run check` before they shipped**: nested `<button>` elements (invalid HTML — cell was a button, badge-row controls inside it were also buttons) fixed by making the cell a `div[role=button]` with keyboard support instead; a non-interactive `<span>` with a click handler (real a11y gap) fixed by making it a real `<button>`. Both required actual restructuring, not suppression.
- `npm run check`: 0 errors, 0 warnings. `cargo test --lib`: still 12/12 passing (no Rust behavior changed, just new plugin registration + Cargo feature).

### Corrections made during the spike (this is exactly what M0 is for)

- **`rcms` → `lcms2`**: the original ADR-0004 research claimed `rcms` was "memory-safe... verified bit-identical to lcms2." That was wrong — `rcms` v0.1.0's own README says *"Currently sparsely implemented and prone to crashing from a `todo!()`."* Swapped to `lcms2` (real bindings to the mature Little CMS C library, `static` feature), which builds cleanly. ADR-0004 updated with a dated finding section; RFC-0001 updated throughout.
- **`rsraw` + MSVC**: `rsraw-sys`'s build script contains `panic!("MSVC is not supported")`. Windows Tauri builds default to the MSVC target, so **`rsraw` as published will not build out of the box on standard Windows** — needs the GNU target, `libraw-rs` instead, or a build-script patch. ADR-0003 updated with this finding; unresolved, needs Windows-side follow-up (see risks below).
- **`rsraw::Error` is not publicly reachable** (kept in a private module, not re-exported) — minor API-maturity gap, worked around in `raw_decode.rs` by converting to `String` via `Display` at each call site instead of using `thiserror`'s `#[from]`.

## Known constraints / open risks

- **This dev environment is still macOS-only** — cannot run a Windows machine directly. Not a real blocker for getting Windows signal though: CI uses GitHub's own Windows runners for that, which is how both the original MSVC failure and its fix were confirmed.
- **`rsraw`'s vendored LibRaw lacks libjpeg** — cannot decode lossy-compressed DNG or other libjpeg-dependent RAW variants, even on macOS. Still open. vcpkg's `libraw` port (used for the Windows fix above) has a `dng-lossy` feature that might fix this too — untried, worth a dedicated look rather than assumed.
- **WebView2's WebGPU support is still unverified** — CI only builds/tests the Rust core, it doesn't launch the full GUI app anywhere yet. The macOS WebGPU spike (ADR-0004) has no Windows equivalent run yet. This was blocked on the MSVC fix before; now that Windows actually builds, this is the next real Windows unknown.
