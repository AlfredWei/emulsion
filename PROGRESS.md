## M2 final slice — Catalog backup (2026-07-29)

Last remaining item on M2's scope list, resumed after being deliberately reprioritized behind the thumbnail-refresh/Filmstrip work above. Per PRD §7.6: prompt on app close with a configurable frequency (every time/daily/weekly/monthly/never), write a timestamped copy of the catalog file to a user-chosen folder kept separate from the working catalog, with an optional integrity check and optional vacuum/compact. Catalog file only — photos are never touched.

Planned via a reviewed design doc. The review corrected the design's central architectural premise: reading Tauri's actual shipped `onCloseRequested` implementation (`node_modules/@tauri-apps/api/window.js`) showed `event.preventDefault()` calling *after* an `await` is Tauri's own documented pattern, not something to engineer around — this eliminated an entire layer of planned startup-snapshot machinery in favor of just re-fetching settings fresh at the top of the close handler. It also flagged a real, deliberately-accepted mutex-hold-duration tradeoff, corrected the first-run default (a `never`-by-default would have made the feature permanently unreachable, since the close-prompt dialog is the *only* place backup settings can ever be changed), and confirmed `rusqlite::backup::Backup` against a WAL-mode source needs no manual checkpoint.

- **New `settings` key/value table**, greenfield — no settings/preferences storage existed anywhere in this codebase before this. `migrate()` inserts idempotent defaults (`backup_frequency: "weekly"`, not `"never"` — see above) on every `open()`, matching this project's existing "not a real migration system, but real enough" precedent.
- **`Catalog::perform_backup`**: canonicalizes and rejects a destination that's the same as or nested inside the app's own data folder (PRD explicitly requires "kept separate," not just a UI hint); runs `PRAGMA integrity_check` first if requested and refuses to write a backup of data already known to be corrupt; runs `VACUUM` if requested; copies via `rusqlite::backup::Backup` — SQLite's real Online Backup API, walking the source's pager rather than raw file bytes, the WAL-safe way to copy a live database without a manual checkpoint step.
- **Real bug found and fixed during empirical verification, not caught by any unit test**: the Online Backup API copies the source's pages verbatim, *including the header byte that records journal mode* — so a backup taken from this app's live WAL-mode catalog came out flagged as WAL-mode too. Confirmed on disk: opening the freshly-written backup file (even just to inspect it with the `sqlite3` CLI) spawned its own `-shm`/`-wal` sidecar files next to it, which is exactly wrong for what's supposed to be one portable, restorable artifact. Fixed by converting the destination connection to `journal_mode=DELETE` immediately after the backup completes — this checkpoints any residual WAL content into the main file and flips the header, confirmed by both a new unit test asserting `journal_mode` is `"delete"` on the finished copy, and by re-running the real smoke test and confirming no sidecar files appeared even after querying the file directly.
- **Deliberate, named exception to this codebase's own "release the mutex before slow work" convention** (`export_images`'s existing precedent): `perform_backup` holds `AppState.catalog`'s lock for its entire duration (integrity check + optional VACUUM + file copy), rather than releasing it before the slow part. Accepted because this is only reachable once, from the close-prompt dialog, immediately before the window is destroyed — documented in a comment matching `export_images`'s own style rather than silently deviating.
- **New `BackupPromptDialog.svelte`** serves both "configure" and "perform" at once, matching real Lightroom's own on-close-only prompt (no persistent settings screen exists anywhere in this app to host anything else). The close handler needed a genuinely new pattern for this codebase: every prior dialog is fire-and-forget from its caller's perspective, but this one needs the close handler to actually *wait* for the user's choice before destroying the window — a small promise-bridge (`showBackupPromptAndWait`/`resolveBackupPrompt`) does that, and "Skip This Time" is always available even if "Back Up Now" fails, so the wait can never trap the user unable to quit.
- **A real bug in my own throwaway verification script, not the shipped code**: the first empirical-verification attempt silently produced no result at all — the smoke test's close sequence called `unlisten()` (copied from the M1 Slice 6 smoke test's precedent) immediately before `getCurrentWindow().close()`, which unregistered the close handler *before* the close event fired, so the window just destroyed itself with zero interception. Root-caused by checking `ps aux` (the process had already exited with no report ever printed) rather than assuming the marker-wait command was still running; fixed by not unlistening before the actual close call.
- **Verified empirically through the real running app**, both branches: forced a stale `last_backup_at` via `sqlite3` on the real dev catalog, drove a real close through the actual `+page.svelte` close handler and the actual `BackupPromptDialog` component (via a throwaway smoke route, script-dispatching a real `MouseEvent` click on the real rendered button, same technique used for the Filmstrip slice above), and confirmed for **Back Up Now**: a real, valid, independently-openable backup file landed at the chosen folder (`PRAGMA integrity_check` → `ok`, correct row data, `journal_mode` → `delete`), and `last_backup_at` updated to the real completion time in the actual catalog; and for **Skip This Time**: no backup file was written, but `last_backup_at` still advanced (so skipping doesn't re-prompt on literally the next close). Smoke route and `tauri.conf.json`'s temporary window-`url` override were removed afterward; the real dev catalog's `settings` rows were reset to fresh defaults rather than left with test-session values.
- `cargo test --lib`: 61/61 passing (5 new: settings round-trip + idempotent defaults, a real on-disk backup that stays independently-openable and keeps `journal_mode=wal` on the *source* while landing `journal_mode=delete` on the *copy*, the destination-not-separate guard, and integrity-check blocking a deliberately corrupted catalog). `npm run check`: 0 errors, 0 warnings.
- **Deliberately deferred, named not silently dropped**: a manual "Back Up Now" trigger outside the close prompt, and any in-app restore UI — no menu/settings surface exists anywhere in this app yet to host either, and PRD's literal ask is prompt-on-close; recovery means pointing the app at a different catalog file, which needs no new UI (matches how real Lightroom itself handles this too).

## Thumbnail refresh after edit + persistent Filmstrip (2026-07-29)

User-requested, reprioritized ahead of catalog backup (the last M2 item): (1) the Library thumbnail never reflected a Develop edit — thumbnails were generated once at import from the "clean" decode and never touched again; (2) `docs/ux/UX-DESIGN.md` specifies a "persistent filmstrip along the bottom of both modules... so context is never lost switching between culling and editing," with a matching (non-interactive) mockup, but it was never actually built. Building the filmstrip also closed a real, separate functional gap: there was previously no way to move between images while already in Develop at all — the only entry point was double-clicking a Library grid cell.

Planned via a reviewed design doc. The review found **one real bug the original design would have shipped**: chaining thumbnail regeneration onto the same promise `pendingSave` tracks would have silently reintroduced the exact "app hangs unable to quit" class of bug M1 Slice 6 already found and fixed once, for the edit-stack flush itself. It also corrected the plan's own cost model (a Develop-preview-cache-hit reuse is a real decode+edit+resize+encode, not free — narrowed the regen hook to real transitions, not every 250ms debounce settle), found a genuine determinism gap in the proposed content-hashing scheme, corrected the exact SQL JOIN needed for a new catalog lookup, and found two real structural gaps in the filmstrip layout the first sketch missed.

- **Thumbnail regeneration reuses the Develop preview cache** (`preview_cache::ensure_develop_preview_for_hash`) rather than a fresh RAW/JPEG decode — cheaper, and the image has already been decoded once anyway by the time Develop is open. `export.rs`'s `apply_edit_stack` (the exact formula the WGSL shader uses) is now `pub(crate)` and reused directly, rather than duplicated.
- **Content-hash-keyed filename, not an overwrite-in-place**: writes to `{image_id}-{blake3(edit_stack_json)[..8]}.jpg`, never touching `{image_id}.jpg`. This codebase has zero cache-busting precedent anywhere (no query params, nothing) — overwriting the same path risked the webview's asset-protocol fetch showing stale cached bytes forever, the same class of bug `preview_cache.rs`'s own module doc already named and solved once for Develop previews. Old thumbnail files are left as accepted orphans, matching that module's already-documented tradeoff. **Corrected framing, not silently assumed**: `develop.js`'s `upsertOp` re-appends the touched op at the end of the array on every change, so reaching identical final values via a different edit order serializes and hashes differently — "bounded pileup, not none," not full dedup idempotency (verified directly: re-regenerating the *same* stack does resolve to the same file, confirmed by test).
- **The real bug, fixed before it shipped**: thumbnail regeneration is fired from a structurally separate promise chain (`regenerateThumbnailFor`), never chained onto `pendingSave`/`pendingIptcSave` — the exact mechanism M1 Slice 6 already fixed once for the edit-stack flush's own hang risk. Never awaited anywhere, including the window-close handler (direct precedent: `generate_missing_thumbnails`' own already-accepted "abandoned on force-quit is fine" posture) — a stale grid thumbnail after a crash is strictly lower stakes than a lost edit.
- **Hook point narrowed to real transitions** (leaving Develop via `switchModule`, switching images via `openDevelop` — captures the OLD `developVersionId` before it's reassigned, mirroring `flushEditStack`'s own already-correct capture-before-reassignment shape — plus `handleExportClick` and the close handler), not the bare 250ms debounce settle, since a user still actively dragging a slider would otherwise trigger a real decode+edit+resize+encode immediately superseded by the next tick.
- **New `Filmstrip.svelte`**, one shared component (matching UX-DESIGN.md's explicit wording) — thumbnail-only cells, no flag/star/color-label badges, matching the reviewed mockup's own explicit simplification for filmstrip cells specifically. **The review's structural fix**: hoisted as a single instance after the whole three-way `{#if library}{:else if developImagePath}{:else}{/if}` block (the first sketch only accounted for two of the three branches, which would have hidden the filmstrip in Develop before any image was ever opened that session — contradicting "persistent"). Clicking a cell in Library selects it (reusing `handleSelect`); clicking a cell in Develop switches the open image via the existing `openDevelop`.
- **The review's second structural fix**: `filteredImages` (driven by the active collection filter) is independent of `developVersionId` — if the open Develop image falls outside the current filter, a naive filmstrip would show no highlighted cell or render empty. `developFilmstripImages` falls back to the unfiltered catalog only in that specific case.
- **Verified empirically through the real app, not just unit tests**: opened a real cataloged RAW file in Develop via the actual `openDevelop`/`handleAdjustmentChange`/`switchModule` code path, confirmed via the filesystem that a new content-hashed thumbnail file appeared, the original import-time thumbnail was left untouched (accepted orphan), and the catalog's `thumbnail_path` pointed at the new file. Separately, since there's no way to screenshot the native window, drove and inspected the **real DOM**: confirmed `Filmstrip` renders the correct cell count in both modules, and dispatched a real `MouseEvent` click on a filmstrip cell in Develop mode, confirming it actually switched `developVersionId` to the clicked image.
- `cargo test --lib`: 56/56 passing (2 new: `get_version_source`'s JOIN, and a real-JPEG test confirming a regenerated thumbnail both reflects the edit and is correctly content-addressed/idempotent). `npm run check`: 0 errors, 0 warnings.

## M2 Slice 5 — Collections (manual) and Smart Collections (rule-based) (2026-07-28)

Last item on MILESTONES.md's M2 scope list requiring new UI (catalog backup is next, and doesn't touch the Library UI at all). The largest slice since Slice 3: the first time the Library rail becomes real/dynamic (a static "Folders > All Photos" placeholder since M1) and the first time this codebase needed a rule/predicate schema (confirmed via grep beforehand: zero prior art for any filter concept anywhere). Planned via a reviewed design doc that found one real, confirmed bug before any code shipped, corrected a factually wrong analogy in the plan's own reasoning, and found a genuinely cheap way to widen scope rather than just possible ones.

- **New tables**: `collections` (id/name/is_smart/rules_json, with a `CHECK` enforcing `is_smart` and `rules_json` stay consistent — a real, correctly-enforced constraint, unlike `keywords`' NULL-parent_id situation from last slice where the equivalent constraint would have silently done nothing) and `collection_images` (composite-PK join, manual collections only — smart collections never get rows there, their membership is always computed, never stored).
- **Rule evaluation stays entirely client-side, but for the right reason this time.** The plan's first draft justified this by claiming "Rust never interprets JSON blobs either, see `EditStack.ops`" — the review caught that this is factually wrong: `export.rs`'s `apply_edit_stack` does interpret `EditStack.ops`, to run the CPU-side export render. The actual, correct reason a JS-only evaluator is fine here: rule evaluation needs no pixel access, and every field it touches (`rating`/`flag`/`color_label`) is already present on every already-loaded `ImageSummary` row. Documented as an explicit schema comment so a future feature needing Rust-side action on "images in a smart collection" reaches for computing the id list in JS and passing it through the existing id-list commands, not a second Rust rule-interpreter.
- **"Keyword" included as a smart-collection field because it turned out to be genuinely cheap, not just possible** — the review found a one-query, no-joins `list_all_image_keywords()` that doesn't touch `list_images()` at all, fetched once. This is real design provenance, not opportunism: the reviewed mockup's own flagship smart-collection example is literally "Smart: 5★ + Untagged," and "Untagged" (has zero keywords) is now supported alongside "has a specific keyword," rating (>=/<=/==), flag, and color_label — all ANDed together, no OR/nesting for V1.
- **Real, confirmed bug caught by the review before it ever shipped**: once the Library grid starts showing a filtered subset (`filteredImages`) instead of the full catalog, `handleSelect`'s Shift-click range-selection logic — which computed range boundaries by indexing into the full `images` array — would have silently pulled hidden, filtered-out images into the selection, which then flows into remove/batch-culling/keyword-assignment against images the user never saw. Fixed by indexing into `filteredImages` instead. **Verified with a smoke test specifically designed to discriminate the bug, not just exercise the happy path**: a 3-image test put two non-adjacent images (a, c) into a collection, deliberately excluding the one between them (b) in catalog order, then Shift-clicked across the filtered pair — confirming `shiftSelectedCount === 2` (not 3) and that no selected id fell outside `filteredImages`. A naive test using adjacent images wouldn't have caught this at all.
- **Another real SQL-correctness catch, also verified rather than assumed**: a smart collection's `count` must come back `null`/`None`, not `0` — `COUNT()` over a `LEFT JOIN` with zero matched rows returns `0`, which would be silently indistinguishable from "not applicable" and invisible in testing (a brand-new smart collection legitimately has 0 real matches too). Explicitly overridden in Rust before serializing; confirmed via both a unit test and the real-app smoke test (`smartCountFromBackend: null`, not `0`).
- **Cache-invalidation discipline**: manual-collection membership is cached client-side per collection id, invalidated by whichever collection id was actually just mutated (add/remove-from-collection), never by whatever collection happens to currently be filtering the grid — those two differ exactly when the toolbar's "Add to Collection…" targets a different collection than the one being viewed, and invalidating the wrong one would silently leave the real target's cache stale.
- **Atomicity precedent followed, not reinvented**: the toolbar's "Add to Collection… → New Collection…" flow uses a new `create_collection_with_images` (one transaction, create + populate together) rather than two separate IPC calls — matching `assign_keyword_path`'s existing create-then-assign shape from the keywording slice, and avoiding the same failure mode (an error between two separate calls leaving an orphaned, empty, confusingly-named collection).
- **Rail becomes real for the first time**: Folders stays exactly as it was (a real disk-folder tree isn't a listed M2 scope bullet anywhere, despite UX-DESIGN.md's aspirational rail description — left untouched, not attempted this slice); a new Collections section lists manual and smart collections with live counts, click-to-filter, hover-reveal delete, and "+"/"+⚡" creation affordances. `.rail` gained `overflow-y: auto` — the review caught that today's rail had no scroll behavior at all (invisible with 2 static lines, a real visual defect the moment a variable-length list was added).
- **Deliberately deferred, matching this codebase's existing precedent for `add_image_with_metadata`/`add_edit_stack`** (lower-level building blocks kept ready without a UI trigger): collection rename, and editing an existing smart collection's rules (the backend `update_smart_collection_rules` command exists and is tested, but has no UI trigger yet — delete-and-recreate is the only way to change a smart collection's rules for now).
- **Verified empirically through the real app**, not just unit tests: created a manual collection with 2 images via the atomic path, confirmed the grid filtered to exactly those 2; ran the Shift-range regression test described above against real data; removed one image from the collection and confirmed membership updated; created a smart collection (rating ≥ 4) and confirmed both the client-side count and the backend's `null` count matched expectations; deleted both collections and confirmed via `sqlite3` that `collections` and `collection_images` were both empty afterward.
- `cargo test --lib`: 54/54 passing (6 new: atomic create-with-images, add/remove round-trip with idempotency, smart-collection rules round-trip + the count-is-null-not-zero assertion, delete-collection cleanup for both manual and smart, `remove_images`'s new orphaned-membership check, the flat keyword-assignment query). `npm run check`: 0 errors, 0 warnings.

## M2 Slice 4 — Keywording (hierarchical): data model + assignment UI (2026-07-28)

Next roadmap item per MILESTONES.md's M2 scope list — a separate bullet from Collections/Smart Collections and from search/filter (the exit criteria literally couple keyword-based search with smart collections as one later criterion, both still fully unbuilt). Scoped to keyword data model + per-image assignment UI only, matching this project's one-bullet-per-slice discipline. Deliberately deferred: keyword management (rename/delete/reparent an existing keyword — no rail/tree-browser UI exists yet to host it), keyword-based search/filter (confirmed genuinely not cheap to fold in — no keyword data flows into `list_images()`, no filter mechanism exists over the Library grid at all today), and the Folders/Collections rail (UX-DESIGN.md and the reviewed mockup both place Keywords in the right panel instead, as its own concern).

Planned via a reviewed design doc that included direct SQLite experiments against the pinned engine (not just reading docs) to settle two real correctness questions before writing code: **`UNIQUE(parent_id, name)` would NOT actually have prevented duplicate top-level keyword names** — SQLite treats every `NULL` as distinct in a UNIQUE check, verified by inserting two `(NULL, 'x')` rows and watching both succeed — so uniqueness is enforced at the application layer instead (find-or-create inside one transaction, safe because `AppState.catalog` is one `Arc<Mutex<Catalog>>`, no concurrent-writer race possible); and **multi-level self-referencing `ON DELETE CASCADE` was confirmed to actually cascade correctly** (deleting a grandparent keyword correctly removed a grandchild, verified directly) now that `foreign_keys` is enabled (M2 Slice 3's fix).

- **New tables** (`keywords`: id/name/parent_id self-referencing; `image_keywords`: composite-PK join table) — no `ALTER TABLE ADD COLUMN` dance needed, since these are brand-new tables, not new columns on existing ones.
- **`Catalog::assign_keyword_path(image_ids, path_segments)`**: one transaction, walks a path like `["nature","birds","owl"]`, finds-or-creates each level, then `INSERT OR IGNORE`s the assignment for every image in the batch — this is what lets typing one keyword into the panel apply it to an entire multi-selection in one round trip, and lets re-typing the same path from a different image reuse the existing hierarchy instead of duplicating it (verified: re-resolving `["nature","birds","owl"]` for a second image returned the identical leaf id, and the keyword table still had exactly 3 rows, not 6).
- **Removal stays anchor-only** (`remove_keyword_from_image`), matching the existing IPTC caption/copyright/contact precedent — only *assignment* batches across a selection, not display or removal. `remove_images` (M2 Slice 3) gained one more explicit `DELETE FROM image_keywords` in its existing transaction, same "don't rely on CASCADE even with the pragma on" discipline as its `image_versions` delete.
- **Real async race caught and fixed before it shipped, not discovered by precedent**: the design review found that this codebase's one existing prop-triggered-`$effect` pattern (`DevelopCanvas.svelte`'s image loader) has no guard against a stale response overwriting newer state if triggered rapidly — but concluded that's tolerable there because switching Develop images is a rare, deliberate action, whereas rapid Library arrow-key/click navigation firing several keyword fetches in flight is a real, likely scenario. `MetadataPanel`'s keyword fetch is guarded: the target `image_id` is captured in the effect closure, and a response is only committed if that id still matches the currently-displayed image when it arrives.
- **Real UX gap caught by the same review**: batch-assigning a keyword to a multi-selection needs visible confirmation beyond the chip list, since the chips only ever reflect the anchor image (same as IPTC) — a newly-assigned keyword landing on N-1 *other* images would otherwise be invisible. Reused this project's existing `statusMessage` pattern (`runImport`/`handleRemoveConfirmed`'s precedent) via a new `onKeywordAssigned` callback: `"Added \"owl\" to 3 photos"`.
- **A planned verification step turned into a design decision instead, because it structurally couldn't be performed**: the plan called for visually checking an HTML `<datalist>`'s rendering in the real WKWebView dev window before committing to it as the suggestion-picker UI (WebKit's native datalist is well-documented to ignore all page theming). This app has no way to screenshot its own native window — a constraint that's held throughout this whole project — so that check was never actually possible. Rather than ship something unverifiable with a known, real theming problem against this panel's otherwise fully dark-themed inputs, swapped to a small manually-rendered, app-themed suggestion dropdown before ever running it, instead of shipping-then-maybe-fixing.
- **Verified empirically through the real app** (script-driven, calling the API functions directly the same way M2 Slice 2 verified IPTC): assigned `nature/birds/owl` to one real cataloged image, confirmed via `sqlite3` exactly 3 keyword rows were created with the correct parent chain; batch-assigned `kyoto` to two images at once, confirmed both got it; removed `kyoto` from just the first image and confirmed the second still had it (anchor-only removal, batch assignment — both directions of the asymmetry actually holding); `get_image_keywords`' returned `path` strings matched the real tree exactly (`"nature / birds / owl"`).
- `cargo test --lib`: 48/48 passing (5 new: nested-path creation/reuse, batch-assign idempotency, anchor-only removal, and `remove_images`'s new orphaned-keyword-assignment check). `npm run check`: 0 errors, 0 warnings.

## M2 Slice 3 — Library multi-select + remove from catalog + batch export: DONE (2026-07-28)

Closes the last piece of the user's original M2 ask ("multi-select, delete from catelogs"). Batch export rode along nearly free: M1 Slice 5 deliberately built `export_batch` to take a `Vec` specifically so this would be "a frontend-only follow-up later," not a backend rewrite. Planned via a reviewed design doc — the review found two real pre-existing bugs before any code was written and one real type-contract break the design itself would have introduced.

- **Real pre-existing bug found while designing removal, not by accident**: `PRAGMA foreign_keys` was never enabled anywhere in the codebase (confirmed by grep) — meaning the schema's `image_versions.image_id ... ON DELETE CASCADE` has been **inert since M1 Slice 1**. A naive `DELETE FROM images` would have silently orphaned `image_versions` rows (invisible garbage `list_images()`'s JOIN would just stop returning, not a visible error). Fixed with a small `enable_foreign_keys()` helper called from both `Catalog::open()` and `open_in_memory()` — but **not** by calling full `harden()` from the in-memory path, which the review caught as a real landmine: `harden()`'s WAL `debug_assert_eq!` would panic every debug-build test, since an in-memory database reports journal_mode `"memory"`, never `"wal"`. `Catalog::remove_images` still deletes child rows **explicitly**, not relying on CASCADE even now that the pragma is live — correctness shouldn't hinge on a per-connection pragma succeeding.
- **New `Catalog::remove_images`**: one transaction per batch, unknown ids are a silent no-op (not an error — a double-fired removal or one racing a refresh should converge on "row is gone," not fail halfway through a batch). Returns each removed row's `thumbnail_path`/`content_hash` (never the source path — removal must not even be *handed* the means to touch an original) so the command layer can clean up app-owned derived files after the DB transaction commits. **The test that matters most**: removing an image makes it re-importable again (`find_by_hash` stops matching) — that's the actual user-facing meaning of "non-destructive," not just "the row disappeared."
- **Command layer**: best-effort `fs::remove_file` on the thumbnail and the content-hash-keyed Develop preview PNG, after the catalog transaction commits, never fatal on failure. Preview deletion by content_hash is safe because import's dedupe guarantees no second row shares a hash. Named, accepted race (same class the project already accepts for preview-cache orphans): a background thumbnail/preview-generation pass snapshotted just before a removal can re-create a file for the now-gone image — an orphan on disk, self-healing in scope, rows can never be resurrected (those passes only ever UPDATE by image_id, which matches nothing post-delete).
- **Frontend selection model**: `selectedIds` (a `Set` of version_ids, reassigned immutably every change — Svelte 5's `$state` doesn't deep-proxy `Set`, so in-place mutation would silently not react) plus `selectedId` retained as the anchor for MetadataPanel/Shift-range/single-image concerns. Standard file-manager click semantics: plain click replaces + moves anchor, Cmd/Ctrl toggles, Shift selects the contiguous range in `images` order from the anchor (computed over the full array — `LibraryGrid`'s virtualization only slices what's *rendered*, never what's *selectable*).
- **Real type-contract break the review caught before it shipped**: `GridCell`'s keyboard Enter/Space path called `onSelect()` with no arguments — once `onSelect` grew an optional `MouseEvent` parameter (needed so modifier keys reach the page-level selection logic), that call site would have been the one thing `npm run check` actually flagged. Fixed by making the event parameter optional; keyboard selection is treated as a plain select.
- **Remove UX**: new `ConfirmDialog.svelte` (same overlay/Escape-gating shell as `ExportDialog`) plus a titlebar Remove button and a Delete/Backspace keyboard shortcut. ## Bug fix: JPEG thumbnails stayed blank forever after import (2026-07-27)

User report, tested and root-caused rather than assumed. Symptom: after importing a JPEG, its Library grid cell stayed a blank placeholder indefinitely, even well after import finished.

- **Metadata was not actually broken** — checked first since the user's report bundled it with the thumbnail symptom. Ran the real extraction path against a real Sony NEX-6 JPEG (copied from a real photo on this machine, not synthetic) both directly (`extract_from_jpeg`) and through the full `import_files` → catalog round trip: camera/lens/exposure/captured-at all landed correctly and immediately. Cell selection wiring (`GridCell` → `LibraryGrid` → `selectedId` → `MetadataPanel`) was also confirmed correct by inspection. Most likely explanation for "no metadata" in the original report: the same blank-looking cell probably discouraged clicking into it, or the user's own test JPEG genuinely had no EXIF (common for downloaded/screenshotted images) — not a code bug.
- **The thumbnail symptom was real, and root-caused, not just patched around.** JPEG thumbnail generation is a fire-and-forget background pass (`import::generate_missing_thumbnails`, M2 Slice 1) that runs *after* the import command already returned its response — by design, so a JPEG-heavy import doesn't block on it. But `+page.svelte` only ever calls `refresh()` (→ `listImages()`) once, right after import (and once more at startup) — nothing ever told it to look again once the background pass actually finished. So the frontend's one-shot snapshot permanently showed `thumbnail_path: null` for the rest of the session, regardless of how long the background pass took or whether it succeeded.
- **Confirmed via a real reproduction, not just code reading**: imported a real 8MB/4000×2658 JPEG through the actual `import_files` command inside the running app, captured the frontend's `images` state immediately after import (thumbnail_path: null, as expected) and again via a direct backend query 4s later (still null) — proving the staleness wasn't just theoretical. A follow-up direct-Rust timing test found the actual cause of *that specific* run's failure: in this project's unoptimized dev build, decoding+resizing a real photo this size took **4.83s**, longer than the 4s window before the app closed — the background `spawn_blocking` task gets abandoned along with the process on quit, so a thumbnail generation that hasn't finished by the time the app closes is lost until the next startup catch-up pass. (Release builds should be dramatically faster since JPEG decode is CPU-bound and debug/dev builds are unoptimized — but the underlying staleness bug would still show up as a delay-then-never-updates symptom in *any* build, just a shorter delay.)
- **Fix**: `+page.svelte` gained `pollUntilThumbnailsReady()` — after any `refresh()` that could have left `thumbnail_path: null` rows (post-import, and the initial startup refresh, which races the app's own startup catch-up pass the same way), it polls `listImages()` every 1.5s (capped at 10 attempts, ~15s total) until no currently-tracked image has a null thumbnail. Bounded deliberately — a genuinely-failed decode (a real, permanent error) shouldn't poll forever; it just stops and leaves the placeholder, which is the correct outcome in that case.
- **Verified the fix actually works, not just that it compiles**: re-ran the same real-photo import through the running app, this time letting `runImport`'s own new polling logic run for real (not artificially closing early) — the frontend's own `images` state went from `thumbnail_path: null` immediately after import to the real generated thumbnail path ~4–8s later, entirely on its own, no manual refresh or restart needed.
- `cargo test --lib`: 42/42 passing (no test changes needed — this was a frontend-only fix, the backend's background-generation behavior was already correct and already covered).

## M1 Slice 6 — Crash-safety hardening + dogfood pass (final M1 slice): DONE (2026-07-26)

Exists to satisfy M1's own exit criteria: "No data loss across app restarts or crashes mid-edit," and "this is the first installable, dogfoodable build." Planned via a reviewed design doc — the review caught a bug that would have silently defeated the flagship fix before any code was written, and one real gap not in the original scope.

- **`flushEditStack()` in `+page.svelte` didn't return its write promise** — every `await flushEditStack()` call site (three existed already: `switchModule`, `openDevelop`, Slice 5's `handleExportClick`) resolved on the next microtask regardless of whether the actual `set_edit_stack` IPC call had landed. Fixed to return the real promise, and to track an in-flight `pendingSave` separately from the debounce timer (a second flush/close can happen while a previous flush's write is still resolving). This was the load-bearing fix everything else in this slice depended on.
- **New: flush the pending edit before the window actually closes.** `getCurrentWindow().onCloseRequested` intercepts a graceful quit, flushes (now correctly awaited), then `destroy()`s. **Named limitation, not hidden**: this protects a graceful quit only (close-button click, or another OS "please close" request routed through the same pipeline `.close()` itself uses per Tauri's own docs) — it cannot help against SIGKILL/a hard crash, which bypasses every in-process handler. Whether macOS Cmd+Q routes through this same path is unverified in this environment.
- **Real capability gap found and fixed along the way**: the app's `capabilities/default.json` only granted `core:default`, which does **not** include `core:window:allow-close`/`allow-destroy`. Without these, the new close-flush handler would have called `event.preventDefault()` and then failed to actually close the window — a user could have gotten **stuck unable to quit the app at all** after dragging a slider, which is arguably worse than the original data-loss bug. Found empirically (the first close-flush smoke-test run failed with `"window.close not allowed"`), not by code review — confirms the value of actually running this rather than assuming Tauri's default permissions were sufficient.
- **Import's two-row insert made atomic**: `import.rs` used to call `add_image_with_metadata` then a separate `add_edit_stack` — two independent auto-commit statements. New `Catalog::add_image_with_edit_stack` (`catalog.rs`) wraps both in one `unchecked_transaction`. Per the design review: a crash between the two old statements left an `images` row `list_images()` silently excluded (no matching `image_versions` row) but that `find_by_hash` still matched on every future import scan — the file became **permanently unimportable** through the normal UI, a disproportionately bad failure mode for how narrow the window was. Fixed by inspection (transactions are correct-by-construction), not by empirically reproducing the microsecond-scale race — padding an import with duplicate-content files to "widen" the window was considered and correctly rejected by the review as not actually testing what it would claim to.
- **SQLite hardened**: WAL mode + `synchronous=NORMAL` on `Catalog::open` (not `open_in_memory`). **Honest framing, not oversold**: the prior default (rollback journal + SQLite's own implicit `synchronous=FULL`) was already durable against process crashes — this doesn't close an existing hole in the "no data loss" criterion (the two fixes above do that). What it actually buys today is more forward-looking hygiene than a realized fix, since `AppState.catalog` is a single `Arc<Mutex<Catalog>>` around one connection — everything already serializes through Rust's own Mutex regardless of journal mode. Cheap and standard to add regardless. Used `pragma_update_and_check` (not `pragma_update`) specifically for `journal_mode`, since `pragma_update` silently swallows the row SQLite returns for that particular pragma and would "succeed" even if WAL failed to engage.
- **Verified empirically, not just by code review** (three real tests through the actual app, no tool to click/screenshot the native window so script-driven triggers substitute for physical interaction, same pattern used throughout this project):
  1. A throwaway `/m1-slice6-smoke` route scheduled a real debounced edit-stack write, then called the real `getCurrentWindow().close()` ~10ms later (well inside the 250ms debounce window) — the close-flush handler intercepted it, and after the process fully exited, `sqlite3` confirmed the edit landed (`exposure: 0.42`, the scheduled value) and WAL mode was active (`-wal`/`-shm` files present, `PRAGMA journal_mode` reports `wal`).
  2. `kill -9` against a running instance with only already-persisted state: `PRAGMA integrity_check` returned `ok` afterward, row counts and edit-stack content were unchanged — confirms the baseline persisted-write path was never the risky part.
  3. `kill -9` timed against a real `import_folder` call (via a throwaway `/m1-slice6-import-kill-smoke` route): the import (only 1-2 real files available in this environment, see below) completed before the kill landed in both attempts — this environment's real files process too fast to reliably land a kill inside the transaction window via external shell-script timing, which is itself consistent with the atomic fix making that window very small. `PRAGMA integrity_check` was `ok` afterward regardless.
- **Real dogfood pass, honestly scaled**: the actual M1 workflow (import → cull → develop → export) was exercised end-to-end across every slice's own verification this session, using this environment's 2 real CC0 sample RAW files — not PRD's literal "hundreds of RAW files" scale, which no larger real RAW set is available here to test. Named plainly rather than implied as tested at scale.
- `cargo test --lib`: 25/25 passing (new `add_image_with_edit_stack_inserts_both_rows_atomically` test). `npm run check`: 0 errors, 0 warnings.

**New named, deferred risks** (this slice's job is naming crash-safety gaps honestly, not fixing every one immediately):
- **`std::sync::Mutex` poisoning**: every catalog command does `state.catalog.lock().map_err(...)?`, and `catalog.rs` uses `.expect(...)` on EditStack JSON (de)serialization. A panic while the lock is held would poison it permanently for the process's lifetime — every later catalog call fails until the user force-quits and restarts. Low-probability today (nothing currently writes invalid JSON), not fixed this slice.
- **A truncated preview PNG from a crash mid-write during background pregeneration would be cached as permanently broken**: `ensure_develop_preview_for_hash`'s cache-hit check (`preview_cache.rs`) is just `out_path.exists()` — a partial file from an interrupted write would pass that check forever, then fail `image::image_dimensions` on every subsequent attempt, with no automatic retry/regeneration. Found while designing (not empirically reproducing) the pregeneration-kill test above. Lower severity than the catalog-side fixes in this slice (affects one cached preview file, not the catalog or the original RAW file — recoverable by deleting the one bad cache file), not fixed this slice.

## M1 Slice 4 — Develop preview cache: DONE (2026-07-26)

Slice 3 shipped Develop decoding the source RAW fresh on every open (explicitly deferred as "correct, simple; caching is a later optimization not a correctness requirement"). In practice this was slow enough that the user asked for a Lightroom-style pre-generated preview mechanism, which was first folded into the roadmap ([PRD §7.2](PRD/PRD.md#72-import)/[§7.6](PRD/PRD.md#76-performance--data-integrity-cross-cutting-not-a-feature-but-a-requirement), [MILESTONES.md's M1 section](PRD/MILESTONES.md#m1--mvp-import--library--basic-develop--export)) and then implemented as this slice.

- **New module `app/src-tauri/src/preview_cache.rs`** owns disk-cache-generation concerns moved out of `lib.rs` (`DevelopPreviewInfo`, `DEVELOP_PREVIEW_MAX_DIMENSION`, `capped_dimensions`). Two entry points: `ensure_develop_preview(path, previews_dir)` (interactive — reads+hashes the file itself since the frontend only supplies a path) and `ensure_develop_preview_for_hash(path, hash, previews_dir)` (background-walk — skips the read+hash entirely on a cache hit, given an already-known hash from the catalog). Both are "ensure a cache entry exists" semantics, never force-regenerate.
- **Real correctness fix, not just a perf one**: the cached PNG's filename now comes from the source file's **content hash** (`blake3::hash(&bytes)`), not a hash of its path (Slice 3's original approach). The path-hash scheme had a latent bug — a file replaced in place with different bytes at the same path would have silently kept serving a stale cached preview forever. Content-hash keying also means a moved/renamed file with identical bytes resolves to the existing cache entry for free, which is a strict improvement on the PRD's own "regenerated when the source file changes (moved/re-imported/replaced)" phrasing.
- **`catalog.rs`**: `ImageSummary`/`list_images()` now expose `content_hash` (nullable, matching the DB column) — this is what makes the background walk cheap: it uses the hash already computed and stored at import time instead of re-reading+re-hashing every RAW file on every walk. (A design review from a Plan subagent caught this before implementation — the naive version, always reading+hashing regardless of the known hash, would have turned "cheap rescan" into O(catalog size in bytes) of disk I/O per import/startup.)
- **Two background triggers**, both calling `preview_cache::pregenerate_missing` (walks `list_images()`, sequential, skips-not-aborts on a per-image failure): after every `import_folder` call (fire-and-forget, doesn't delay the command's response), and once at app startup in `lib.rs`'s `.setup()` — the startup pass is what catches up images cataloged before this feature existed (the app's real catalog already had one such image from Slice 3 testing).
- **Deliberately sequential, not a worker pool** — avoids CPU/memory spikes decoding many RAW files at once. Accepted, explicitly-named tradeoff: with no priority queue, a large first-run backlog walk can transiently compete for CPU with an interactive Develop-open decode for whatever image the user just clicked into. Self-healing (worst case: one duplicate decode), not a blocker.
- **No frontend changes needed** — `DevelopCanvas.svelte`'s existing "Decoding…" overlay already covers every cache-miss case (first-ever open, background walk hasn't reached that image yet, app restarted mid-walk).
- **Verified empirically, not just via tests**: cleared the real `previews/` directory, relaunched the actual app with zero frontend interaction, and confirmed the startup catch-up pass regenerated `previews/{content_hash}.png` for the real cataloged image — filename matched the catalog's stored `content_hash` exactly. Relaunched a second time and confirmed the PNG's mtime was byte-for-byte unchanged (`Jul 26 11:47:22` both times), proving the second run hit the cache and did not redecode.
- `cargo test --lib`: 18/18 passing, including new real-file-gated tests in `preview_cache.rs` (cache-hit skips redecode, verified via unchanged mtime; identical content at two different paths resolves to the same cache entry; `pregenerate_missing` against a real `scan_and_import`'d catalog produces the expected cache file). `npm run check`: 0 errors, 0 warnings.

Worth remembering for future config-only changes (e.g. the `spike`/`spike-revert` Makefile targets), not fixed here since it's a dev-loop quirk, not a shipped-code bug.
